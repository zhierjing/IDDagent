## 第 3 页：项目背景

**要点**

- **系统定位**：面向银行客户经理的智能尽调助手，一句话即可发起企业风险识别、信息核实、尽调报告生成等操作
- **技术栈**：Spring Boot WebFlux（响应式后端）+ React/TypeScript（前端）+ SSE 事件流 + LLM（轻量模型 + 主模型级联）
- **能力范围**：13 个已注册技能（企业查询 ×9、风险预查、营业执照核实、报告生成、历史尽调查询）
- **核心挑战**：用户一句话可能包含多个意图（"核实A公司信息并做风险识别"），且表达模糊、口语化严重

**图示建议**：系统截图或功能架构简图（用户 → 对话界面 → 后端 → 技能库/LLM/数据）。

## 第 4 页：核心问题——为什么不能"全 LLM 一把梭"？

**要点**

- 早期方案：单层 LLM + 17 条硬编码规则做意图路由，存在四大痛点：

| 问题 | 表现 |
|------|------|
| 不可解释 | 同一句话在不同上下文可能路由到不同技能，无法测试 |
| 冲突无仲裁 | 相似技能（生成报告 vs 历史查询）靠 prompt 硬碰硬 |
| 无澄清能力 | 意图模糊时只能降级为闲聊 |
| 不支持多意图 | 复合请求被强制二选一，无法依次执行 |

- 目标：**确定性优先、LLM 兜底**，让意图识别可解释、可测试、低成本

**图示建议**：四象限痛点图，或"单层 LLM 黑盒"与"分层确定性架构"的对比图。

## 第 5 页：总体架构——一条用户消息的完整旅程

**要点（7 步链路）**

1. **主流程分支裁决**：状态机入口，按优先级处理恢复协议、交互协议、穿插判定等
2. **三层意图路由**：确定性树匹配 → LLM 仲裁 → LLM 兜底（回答"用户要做什么"）
3. **结构化决策**：skill / chat / clarify / multi / preset_reply
4. **任务规划**：TaskPlanner 生成有序执行计划（回答"按什么顺序做"）
5. **技能执行管道**：逐任务执行、参数共享、任一任务缺参即暂停
6. **SSE 事件流**：结果卡、任务清单卡、澄清卡、询问卡实时推送到前端
7. **流尾检查**：有挂起的旧任务则主动询问"是否继续"

**一句话总结**：意图识别回答"用户要做什么"，任务规划回答"按什么顺序做"，意图穿插回答"做一半时用户换需求了怎么办"。

**图示建议**：横向 7 步流程图（用户消息 → 路由 → 决策 → 规划 → 执行 → 事件流 → 前端），每步标注核心类名。

## 第 6 页：核心设计原则

**要点**

- **确定性优先**：能确定性判断的绝不让 LLM 决策——80% 的常见意图在毫秒级确定性路由，唯一候选还能零 LLM 直接提取参数
- **LLM 只做"选"不做"猜"**：有候选时只仲裁/提取参数，无候选时才完整规则兜底
- **一次调用识别，一次规划**：多意图识别与任务规划合并到一次 LLM 决策，排序交给确定性代码
- **用户选择是最高置信度的意图**：澄清卡片点击后直连路由，不再让 LLM 二次误判
- **模型级联降成本**：轻量模型先判，疑难场景（低置信度/多意图/澄清）才升级主模型

**图示建议**：天平图（左：确定性规则，右：LLM，配文案"能确定的不麻烦 LLM"）。

## 第 7 页：单意图识别——三层架构总览

**要点**

```
第①层  分层意图树确定性匹配（零 LLM，毫秒级）
         ├─ 唯一候选 → 直接参数提取（零 LLM）
         ├─ 核实对象不明 → 澄清卡片
         └─ 多候选 → 第②层
第②层  LLM 仲裁（多候选时：选一个 / multi / clarify / chat）
第③层  LLM 完整规则兜底（零候选时：19 条决策规则）
```

- 三层的调用成本递增、确定性递减：**能少用 LLM 就少用**

**图示建议**：漏斗图/金字塔图，从上到下标注"零 LLM → 一次 LLM → 完整规则"，旁边标注触发条件。

## 第 8 页：第一层——分层意图树（零 LLM 确定性匹配）

**要点**

- 意图规则天然呈分层结构（场景 → 对象 → 行为 → 信息类型），用**树**而不是扁平关键词表表达
- 四域组织：A 尽调业务域 / B 核实域 / C 法人查询域（风险、工商、海关子域 + 独立叶子）
- 关键设计：
  - **域 = 纯组织分组，不设匹配门槛**，行为词下放到叶子条件，避免跨域误剪
  - **互斥由树结构承担**（如"历史/得分/最新"三选一由 defaultLeaf 表达），不再需要排除词互相否决
  - **defaultLeaf 兜底 + 全局意图词黑名单**：兄弟全未命中才激活兜底叶子，且黑名单词出现即放弃，防止"查询/查一下"这类宽松词劫持具体意图
  - **matchable 预留节点**：未开通业务可正常命中但返回"该业务暂未开通"，不静默落到其他技能
- 匹配算法：DFS + 条件组，剪枝提效；同技能多叶子命中自动去重

**图示建议**：意图树结构图（ROOT → 四域 → 叶子，用不同颜色标 defaultLeaf、matchable、预留叶子）。

## 第 9 页：条件组语义——一个节点的"准入条件"

**要点**

| 条件维度 | 语义 | 示例 |
|----------|------|------|
| `mustAny` | 任一命中即满足；空列表 = 该维度宽松 | 股东：股东/股权结构/股权分布 |
| `mustAll` | 必须全部命中 | e缴费尽调：必须含"e缴费"且含"尽调/尽职调查" |
| `mustNot` | 任一命中即否决（剪枝） | 生成报告排除"历史/查询/以前" |
| 附加维度组 | 每组任中其一、组间 AND | 营业执照核实：须含"营业执照"且含"核实/核对/核验" |

**讲稿提示**：用"查一下小米科技的风险情况"举例——命中 C1 风险叶子；基本信息兜底叶子因黑名单含"风险"而否决，实现跨域互斥。

**图示建议**：一个叶子节点的条件卡片示意图，四个维度分开展示。

## 第 10 页：唯一候选的确定性执行路径（零 LLM 优化）

**要点**

- 树匹配唯一命中且为可执行技能时，**优先直接提取参数、跳过 LLM**：
  1. 统一信用代码字段 / 18 位裸代码 → 直接提取
  2. 企业名 → 统一公共清洗链（剔除查询对象词/动作词）
  3. 消息未含企业名 + 上下文引用词（"这家/该公司"）→ 上下文记忆补全
  4. 全部失败 → 回退 LLM 参数提取（不硬凑）
- 提取成功 → 整条链路**零 LLM 调用**：低延迟、零成本、可测试

**讲稿提示**：强调这是"确定性优先"原则的最大收益点——最常见的查询类意图，用户体感是毫秒级响应。

**图示建议**：流程图（唯一候选 → 4 步提取链 → 零 LLM 完成；失败才回退 LLM）。

## 第 11 页：第二层——LLM 仲裁（多候选时）

**要点**

- 触发条件：树匹配出多个候选（如"查一下风险历史得分"同时命中历史与得分）
- 仲裁输入：候选列表 + 用户输入 + 对话历史 → LLM 裁决为 skill / multi / clarify / chat
- 关键机制：
  - **置信度阈值 0.6**：仲裁置信度 < 0.6 → 后端自动改写为澄清决策（发候选卡让用户选），≥ 0.6 正常路由
  - **决策归一化防幻觉**：LLM 输出注册表之外的技能名 → 强制降级 chat
  - **支持 multi 输出**：仲裁层即可一次识别多个意图
- 为什么先仲裁而不是直接澄清？仲裁成本（一次 LLM）远低于澄清交互（一轮人机往返）

**图示建议**：分流图——多候选 → 仲裁 → (置信度≥0.6 → 路由；<0.6 → 澄清卡)。

---

## 第 12 页：第三层——LLM 完整规则兜底（零候选时）

**要点**

- 触发条件：树匹配零命中（如"你好"、"云禾科技"无行为词）
- 19 条决策规则（与意图树手工同步）完成：
  - 规则化意图判定（含"风险+历史"→ 对应技能）
  - **多意图检测**：多个互不排斥的触发词 → action=multi
  - 上下文记忆规则（"换一家"→ 匹配最近同类型技能；"再查2024年的"→ 变更查询条件）
  - **模糊输入 → clarify 而非 chat**：意图不明但有多种合理解读时引导用户选择
- 模型级联：轻量模型先判，疑难场景升级主模型重判

**讲稿提示**：强调兜底层是"最后防线"，命中率低但覆盖面广，保证任何输入都有合理出口。

**图示建议**：兜底决策树示意图，或"空候选 → 规则 → 澄清/闲聊"流程。

## 第 13 页：意图澄清交互闭环

**要点**

- 触发：仲裁低置信度（<0.6）、LLM 显式 clarify、核实对象不明（如"核实一下"）
- 闭环流程：
  - 后端发 `intent_candidates` 事件（候选技能 + 原始用户输入 + frameId + interactionId）
  - 前端渲染候选卡片，用户点击 → 发送结构化协议 `{"action":"select_intent", ...}`
  - 后端校验帧归属（旧卡点击被拒绝）→ 从澄清卡恢复原始输入 → LLM 提取参数 → 直接执行
- 价值：
  - **用户的选择是最高置信度的意图**，不再让 LLM 二次误判
  - 原始输入随卡持久化，避免参数丢失被上下文自动填充成上一轮企业
  - interactionId + frameId 让"哪张卡属于哪个任务"可精确定位

**图示建议**：对话气泡时序图（用户输入 → 澄清卡 → 点击 → 结果卡）。

## 第 14 页：多意图识别——Multi-Intent Pipeline

**要点**

- 识别位置：仲裁层与 LLM 兜底层，LLM 输出 `action=multi` + `skills` 数组（按依赖顺序排列）
- 判定规则：输入中出现**多个互不排斥的意图触发词**（如"核实营业执照并做风险识别"）
- 示例决策：

```json
{ "action": "multi",
  "skills": [
    { "skill": "verify_business_license", "params": { "company_name": "A公司" } },
    { "skill": "check_company_risk",      "params": { "company_name": "A公司" } }
  ]}
```

- 参数共享：company_name / credit_code 由上下文记忆统一注入，前序任务输出自动供后续任务使用，用户无需重复输入

**图示建议**：一条复合句 → 拆分为多个技能卡片的示意图。

## 第 15 页：任务规划——TaskPlanner 确定性规则

**要点**

- 核心思想：**LLM 只输出"有哪些意图"，"按什么顺序执行"交给确定性代码**——排序规则可测试、可解释
- 五条确定性规则：

| 规则 | 说明 |
|------|------|
| 去重 | 同一技能只保留一次（合并参数） |
| 技能合法性过滤 | 未注册技能直接跳过（防御 LLM 幻觉） |
| 报告依赖前置 | `generate_report` 与查询类技能同现时强制排最后（报告需要前置结果作素材） |
| 例外不重排 | 历史尽调查询不产生素材，与报告同现保持用户陈述顺序 |
| 依赖标注 | 报告任务 dependsOn 前序任务；共享 company_name / credit_code |

- 单技能执行 = 长度为 1 的计划，规划层零干预

**讲稿提示**：用"核实A公司并生成尽调报告"举例：plan = [核实 → 报告]，报告自动排最后。

**图示建议**：排序规则示意图——"用户输入顺序" vs "重排后顺序"对比。

## 第 16 页：执行管道——从计划到结果

**要点**

```
handleMulti:
  1. plan = TaskPlanner.plan(skills)
  2. 分配 frameId（一个独立意图 = 一个执行帧）
  3. 创建 PlanRuntime（步骤全 PENDING，状态视图）
  4. 持久化任务清单卡（刷新不丢）
  5. 发 planning 事件："我将依次为您执行：①营业执照核实 ②风险预查"
  6. 逐任务执行：
     - task_start 事件（第几步/共几步）
     - 上下文记忆补全参数
     - 结果事件复用单技能事件类型（前端卡片零改动）
     - 任务完成 → task_done + 步骤置 DONE
     - 全部完成 → 绿色完成卡 + Plan COMPLETED
```

**图示建议**：任务清单卡截图（plan 卡 → switch 卡 → complete 卡三形态）。

## 第 17 页：暂停-恢复机制

**要点**

- 任一任务缺参数（`info_needed`）、企业模糊（候选卡）、模板选择 → **管道暂停**：
  - 当前任务参数 → `pendingSkill`
  - 剩余任务队列 → `pendingPipeline`
  - 前端任务清单卡标记 paused
- 用户补充信息后自动续跑：先完成当前任务 → 弹栈执行剩余任务 → 全部完成清理
- 恢复前用最新上下文企业刷新剩余任务参数，防止旧快照简称再次弹候选卡
- 优先级：`pendingPipeline` 恢复 > `pendingSkill` 恢复（管道 + 管道内当前位置）

**图示建议**：时间轴图——任务① 完成 → 任务② 暂停（等待输入）→ 用户补充 → 继续②③。

## 第 18 页：Plan 状态投影——看得见的任务进度

**要点**

- 设计哲学：**Plan 是 Pipeline 的状态投影，不是新的执行引擎**——只记录状态，不参与调度
- 状态机：步骤 PENDING → RUNNING → WAITING_INPUT / WAITING_EXTERNAL → DONE
- 整体计划：PENDING / RUNNING / WAITING_INPUT / WAITING_EXTERNAL / COMPLETED / ABANDONED
- 单向投影：禁止 Plan 反过来决定 Pipeline 执行什么
- 挂起时 PlanRuntime 随执行帧快照保存（穿插期间新意图的计划不覆盖旧计划），恢复时还原

**图示建议**：任务清单卡上的状态流转示意（每一步的状态徽标变化）。

## 第 19 页：亮点延伸——意图穿插（执行中换需求）

**要点**

- 场景：多意图管道暂停时（如等待模板选择），用户发来**与当前任务无关的新意图**（"查询B公司历史尽调"）
- 问题：若不做区分，该消息会被当作补充信息吞进管道恢复流程
- 方案：六层判定"补充信息 vs 新意图"（顺序不可调）：

| 层 | 判定手段 | 判为新意图的条件 |
|:---:|------|------|
| ① | 结构化协议 | 【意图选择】→ 新意图；【模板选择】→ 补充 |
| ② | 显式穿插信号词 | 顺便/另外/再帮我/先查一下… + 独立任务请求 |
| ③ | 预期输入 | 纯企业名/信用代码/日期/候选序号 → 补充 |
| ④ | 确定性树匹配 | 命中技能 ≠ 当前暂停技能 → 新意图 |
| ⑤ | 上下文转移 | 含新企业名 + 查询行为词（"阿里的股东呢？"） |
| ⑥ | LLM 二分类 | 兜底（失败保守返回 supplement） |

- 前五级零 LLM、可测试；误判代价可控（最多多一次询问）

**图示建议**：分叉图——暂停中的管道 vs 新消息，六层漏斗判定。

## 第 20 页：ExecutionFrame 挂起栈——断点再续的核心

**要点**

- 判定为新意图 → **全量挂起**当前管道（打包成执行帧压栈）→ 执行新意图 → 新意图结束 → 主动询问"是否继续旧任务"
- 执行帧 = 可完整保存、挂起、恢复、放弃的**任务运行现场**，包含：剩余任务队列、完整计划快照、暂停中任务、企业上下文、附件、Plan 状态、异步事件
- 为什么存快照？穿插期上下文企业被改成 B，恢复旧管道必须以快照里的 A 为基准续跑
- **嵌套穿插**：A 中穿插 B、B 中再穿插 C → 栈 LIFO，恢复只弹栈顶，逐层决定
- 恢复校验：结构化协议必须匹配栈顶帧，旧卡点击被拒绝（防串帧）
- 交互 ID 化：每张交互卡携带 frameId + interactionId，后端校验归属

**图示建议**：栈示意图（Stack: A → B，Current: C），或"穿插-询问-恢复"完整时序图。

## 第 21 页：异步任务与管道同步（工程亮点）

**要点**

- 报告生成是异步链路：用户跳转 H5 编辑页、上传附件 → 报告后台生成
- 同步机制：前端轮询报告状态 → 完成回调推进管道（最后任务 → 完成卡收尾；中间任务 → 继续续跑）
- 穿插期间报告完成 → 完成事件随帧保存，恢复该层时**就地推进**（防止推进动作丢失导致死锁）
- 轮询去重双保险：前端按 reportId 去重 + 后端 consumed 标记，防止 3s 轮询刷屏
- 防御：报告任务从未创建（用户没上传附件就关闭）→ 恢复时重新引导跳转，防止管道永久挂起

**图示建议**：泳道图（用户 / 前端 / 后端 / 报告服务）展示轮询-回调-推进时序。

## 第 22 页：技术亮点总结

**要点**

1. **确定性优先架构**：三层路由让 80% 意图毫秒级确定，LLM 只做仲裁与兜底——可解释、可测试、低成本
2. **树结构表达互斥**：层级互斥由树承担，defaultLeaf + 黑名单防宽松词劫持，matchable 预留未来业务
3. **LLM 出集合、代码出顺序**：任务规划的排序、去重、依赖全部确定性实现
4. **状态快照化**：执行帧 + Plan 投影，穿插/恢复/刷新不丢任务
5. **协议结构化**：交互 ID 化 + 帧归属校验，旧卡点击不污染当前任务
6. **异步解耦**：报告异步生成 + 事件入帧 + 轮询去重，同步管道与异步链路正确衔接
