## 一、背景与目标

当前系统的意图识别由 `CoordinatorService` 单层 LLM 路由实现（17 条硬编码决策规则 + DeepSeek 调用），存在以下问题：

| 问题 | 现状表现 |
|------|----------|
| 路由不可解释 | 决策完全依赖 LLM 黑盒，同一句话在不同上下文可能路由到不同技能 |
| 意图冲突无仲裁机制 | 意图相似的技能（如 `generate_report` 与 `query_due_diligence_reports`）靠 prompt 规则硬碰硬，优先级不透明 |
| 无澄清能力 | 意图模糊时只能降级为普通聊天（`chat`），无法引导用户选择 |
| 不支持多意图 | 复合请求（如"核实A公司信息并做风险识别"）只能被强制二选一，无法依次执行 |
| 无任务规划 | 技能执行只有"单技能一次调用"，没有执行顺序、依赖、参数传递的概念 |

本方案的目标：

1. **单意图识别**：确定性前置匹配 + LLM 仲裁 + 结构化决策 + 意图澄清闭环（方案 A/B/C/D）。
2. **多意图识别**：一次输入解析出多个技能意图，按任务规划顺序依次执行（Multi-Intent Pipeline）。
3. **任务规划**：将多意图转换为有序执行计划，处理依赖关系与参数传递，支持"执行中暂停-补充-继续"。

### 2.2 意图识别现状（`CoordinatorService`）

- `routeIntent(userMessage, history)`：构建 17 条决策规则的 system prompt → 调 DeepSeek（temperature=0.1, max_tokens=300, thinking disabled）→ `parseResponse` 解析。
- `parseResponse` 只接受两种合法决策：`{"action":"skill","skill":...}` 与 `{"action":"chat",...}`；未知技能名降级为 `chat`。
- 多轮上下文：靠 system prompt 规则 5/7 描述（"上一轮是技能结果则继续同技能"），依赖 LLM 记忆，无确定性机制。

### 2.3 技能执行现状（`ChatController`）

- `chatStream` 主流程：`pendingSkill` 分支（重试上限 3 次，防死循环）→ 空消息直接 `handleChat` → 否则 `routeIntent`。
- `handleSkill`：上下文记忆补全（`credit_code`/`company_name`/`_attachment_url` 注入）→ `skillRegistry.invoke`（隔离到 `boundedElastic` 线程池）→ 按技能返回的 `action` 分支发事件：
  - `summary` / `detail` → `potential_customer_summary` / `potential_customer_detail`
  - `candidates` → `company_name_candidates` + `setPendingSkill`
  - `info_needed` → 文本提示 + `setPendingSkill`
  - `result` / `ambiguous` / `not_found` → 按技能名映射事件类型（`risk_check_result` / `historical_dd_query_result` / `information_check_result` / `company_query_result`）+ 上下文更新 + 清理 pending + `follow_up_suggestion`

### 2.4 上下文记忆（`ContextMemoryService`）

`ConversationContext` 现有字段：`companyName`、`creditCode`、`pendingSkillName`、`pendingSkillParams`、`pendingSkillRetry`、`attachmentUrl`。

### 2.5 前端现状

- `types/index.ts`：SSEEventType 含 `thinking/meta/text_start/text_delta/text_done/risk_check_result/report_generate_result/information_check_result/historical_dd_query_result/company_query_result/follow_up_suggestion/company_name_candidates/need_date_range/done/error`。
- `useChat.ts`：`sendMessage` 回调内按 `event.type` switch 分发；`task_start` 处理中，进入新任务（order>1）新建 `switch` 切换卡的同时**同步更新第一张 `plan` 卡的 currentOrder**，使首卡始终反映最新执行进度；`done` 时新建 `complete` 完成卡。
- `ChatMessage.tsx`：按 `extra.action` 与 `_skill_name` 路由渲染卡片；`company_name_candidates` 渲染 `CompanyNameSelector` 澄清卡片。
- `TaskProgressCard.tsx`：任务清单卡片（`extra.action='pipeline'`），按 `kind` 分三形态——`plan` 初始执行计划卡 / `switch` 任务切换卡 / `complete` 最终完成卡。
- 卡片持久化：初始 plan 卡（`handleMulti` 落盘，`kind='plan'`）与 switch/complete 卡（`executePipeline` 内 `persistPipelineCard` 追加落盘）均以 `{"action":"pipeline",...}` JSON 存为 assistant 消息；切换会话/刷新后由 `App.tsx` 解析 `extra` 恢复渲染。`executePipeline` 每次 `task_start` 同步更新首卡 currentOrder（`updatePipelinePlanCardOrder`），保证重载后首卡进度正确、切换卡/完成卡不消失。
- 报告模板选择协议（`generate_report` 暂停恢复）：模板列表卡（`stage='templates'`）点击模板后前端发送固定格式文本消息 `【模板选择】<template_id>`；后端 `handleSkill` 开头解析该前缀并注入 `template_id`，重入技能直接返回跳转信息（`stage='redirect'`）。模板阶段在 `handleSkill` 中视为未完成任务（`templateStage=true`）：不发送 `task_done`、设置 `pendingSkill` 暂停管道（多意图时追加 `pipeline_paused`）、跳过 pendingSkill 清理与 follow_up 预测——避免多意图管道在选模板前被误判为已完成；事件类型为 `report_generate_result`。

## 三、总体架构

```
用户输入（含对话历史）
        │
        ▼
┌─────────────────────────────── 三层意图路由（单意图） ───────────────────────────────┐
│  ① IntentMatcher 确定性前置匹配（Skill 元数据：keywords/excludeKeywords/priority/conflictGroup） │
│     ├─ 候选唯一 → 直接路由，LLM 仅做参数提取（buildParamExtractionPrompt）              │
│     ├─ 候选多个 → ② LLM 仲裁（输出 skill/confidence/alternatives）                     │
│     └─ 无候选   → ③ LLM 完整规则兜底（现有 17 条规则增强）                              │
└──────────────────────────────────────────────────────────────────────────────────────┘
        │  决策结果（action: skill | chat | clarify | multi）
        ▼
┌───────────────────────────────── 任务规划层（TaskPlanner） ─────────────────────────────┐
│  multi 决策 → 生成有序执行计划 plan（任务列表 + 依赖 + 参数传递）                          │
│  单技能决策 → 视为长度为 1 的 plan                                                        │
└──────────────────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌────────────────────────── 技能执行管道（Multi-Intent Pipeline） ────────────────────────┐
│  按 plan 顺序执行；参数共享（上下文记忆注入）；                                          │
│  任一任务返回 info_needed/candidates → 暂停，记录 pendingPipeline，补充后继续             │
└──────────────────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
   SSE 事件流（复用现有事件类型 + 新增 intent_candidates / planning）
```

核心原则：

- **确定性优先**：能用元数据规则确定的意图不依赖 LLM，保证可解释、可测试。
- **LLM 只做"选"不做"猜"**：有候选时 LLM 只仲裁/提取参数，无候选时才完整规则兜底。
- **一次调用识别，一次规划**：多意图识别与任务规划合并到一次 LLM 决策（`action=multi` 携带 `skills` 数组），由 `TaskPlanner` 确定性后处理排序与依赖校验。

## 四、单意图识别

### 4.1 方案 A：技能元数据化

#### 4.1.1 `Skill` 类扩展字段

`Skill.java` 在现有 `name/description/handler/parameters` 基础上新增：

| 字段 | 类型 | 含义 | 默认值 |
|------|------|------|--------|
| `label` | `String` | 中文展示标签（澄清卡片、规划文本使用） | `name` |
| `keywords` | `List<String>` | 触发词：命中任意一个即产生该技能候选 | 空 |
| `excludeKeywords` | `List<String>` | 排除词：命中任意一个则否决该技能候选 | 空 |
| `objectType` | `String` | 指向对象类型：`法人` / `自然人` | `法人` |
| `priority` | `int` | 同冲突组内优先级（数值大者胜） | 0 |
| `conflictGroup` | `String` | 冲突组标识（同组互斥，需优先级裁决或仲裁） | `""` |

新增链式方法 `withMeta(...)` 供注册时声明元数据：

```java
public Skill withMeta(String label, List<String> keywords, List<String> excludeKeywords,
                      String objectType, int priority, String conflictGroup) {
    this.label = label;
    this.keywords = keywords;
    this.excludeKeywords = excludeKeywords;
    this.objectType = objectType;
    this.priority = priority;
    this.conflictGroup = conflictGroup;
    return this;
}
```

同时 `toPromptDesc()` 自动附带触发词/排除词，使 LLM 兜底 prompt 与确定性匹配共用同一份元数据，避免双份维护：

```text
- **check_company_risk**: 企业风险预查…
  参数: credit_code (示例: …), company_name (示例: …)
  触发词: 风险预查, 风险筛查, 风险识别, 企业风险, 风险报告, 风险预检, 风险
  排除词: 得分, 评分, 评价, 打分
```

> 未调用 `withMeta` 的技能（无元数据）不参与确定性匹配，仅参与 LLM 兜底。

### 4.2 方案 B：确定性前置匹配与冲突仲裁

#### 4.2.1 `IntentMatcher`（新建组件）

新增 `com.IDDagent.skill.IntentMatcher`，构造时注入 `SkillRegistry`，提供确定性匹配能力：

```java
@Component
public class IntentMatcher {
    /** 匹配输入文本，返回候选技能列表（已按 priority 降序） */
    public List<SkillCandidate> match(String userMessage) { ... }

    /** 同冲突组内按 priority 保留最高者（平票则全部保留交给 LLM 仲裁） */
    public List<SkillCandidate> resolveConflict(List<SkillCandidate> candidates) { ... }
}

public record SkillCandidate(String skillName, String label, String conflictGroup,
                             int priority, List<String> matchedKeywords, double score) {}
```

匹配算法（`match`）：

1. 遍历注册表中所有**声明了元数据**的技能；
2. 若输入包含任一 `excludeKeywords` → 直接否决该技能；
3. 统计命中 `keywords` 的数量与最长命中词长度，计算 `score = 命中词数 * 10 + 最长命中词长度`；
4. 命中至少 1 个触发词 → 产生候选，按 `score` 降序返回。

`resolveConflict` 裁决规则：

- 同 `conflictGroup` 内，仅保留 `priority` 最高的候选（平票保留多个 → 交给 LLM 仲裁）；
- 跨组候选不互相否决，全部进入仲裁候选列表。

#### 4.2.2 `SkillRegistry` 扩展

新增方法：

| 方法 | 说明 |
|------|------|
| `getSkills()` | 返回全部技能（供 IntentMatcher 遍历） |
| `getSkillLabel(name)` | 取技能中文标签（取不到回退为 name） |
| `matchByKeywords(text)` | 便捷入口：内部调用 IntentMatcher |

#### 4.2.3 三层路由流程（`CoordinatorService.routeIntent` 重构）

```
输入 userMessage
   │
   ├─ ① candidates = IntentMatcher.match(userMessage)
   │     ├─ 空 → ③ LLM 完整规则兜底（现有 17 条规则增强版）
   │     ├─ 唯一候选 → 直接决策 action=skill，LLM 仅提取参数
   │     │              （buildParamExtractionPrompt：给定技能，只输出 params）
   │     └─ 多候选 → resolveConflict 裁决
   │           ├─ 裁决后唯一 → 同上走参数提取
   │           └─ 仍多候选 → ② LLM 仲裁
   │                        （buildArbitrationPrompt：给定候选列表 + 用户输入 + 历史，
   │                          输出 {"action":"skill"/"clarify","skill", "confidence",
   │                               "alternatives":[...], "reason"}）
   │
   ▼
结构化决策（见 4.3）
```

仲裁 prompt 输出契约（方案 C）：

```json
{
  "action": "skill",
  "skill": "generate_report",
  "confidence": 0.85,
  "alternatives": ["query_due_diligence_reports"],
  "params": { "company_name": "小米科技" },
  "reason": "用户提到'尽调报告'且无'历史'字眼，判定为生成报告而非历史查询"
}
```

### 4.3 方案 C：结构化决策输出

`parseResponse` 扩展支持四种 `action`，决策 JSON 统一 schema：

```json
{ "action": "skill | chat | clarify | multi", "...": "见下表" }
```

| action | 必填字段 | 说明 |
|--------|----------|------|
| `skill` | `skill`, `params`, `confidence`, `reason` | 单意图路由，`alternatives` 可选（仲裁时回传） |
| `chat` | `reason` | 普通对话 / 无意图匹配 |
| `clarify` | `candidates`（候选技能数组）, `message`, `reason` | 意图模糊，转澄清（见 4.4） |
| `multi` | `skills`（数组）, `reason` | 多意图（见第五章） |

**置信度阈值**：`CLARIFY_CONFIDENCE_THRESHOLD = 0.6`。

- 仲裁决策 `confidence < 0.6` → 后端自动改写为 `clarify` 决策（把 `alternatives` + 首选技能组成候选列表，发 `intent_candidates` 事件）；
- `confidence >= 0.6` → 正常路由；
- LLM 显式输出 `clarify` → 直接走澄清。

**备选纠错（postProcessArbitration）**：仲裁返回的 `skill` 若不在候选列表中且不在注册表中 → 纠正为 `confidence` 最高的候选，避免 LLM 输出注册表之外的技能名。

### 4.4 方案 D：意图澄清交互闭环

适用场景：多候选仲裁低置信度、或 LLM 显式 `clarify`。闭环协议如下：

#### 4.4.1 后端：`intent_candidates` 事件

`ChatController` 新增 `handleClarify`，发送：

```json
{
  "type": "intent_candidates",
  "message_id": "<assistantMsgId>",
  "conversation_id": "<convId>",
  "message": "您的问题可能有多种理解，请选择您想要的操作：",
  "candidates": [
    { "skill": "generate_report",    "label": "尽调报告生成",       "description": "生成一份尽调报告" },
    { "skill": "query_due_diligence_reports", "label": "历史尽调报告查询", "description": "查询历史尽调报告" }
  ]
}
```

#### 4.4.2 前端：`IntentSelector` 澄清卡片

- `useChat.ts` 新增 `case 'intent_candidates'`：将数据以 `extra.action='intent_candidates'` 注入流式消息。
- `ChatMessage.tsx` 新增 `intent_candidates` 渲染分支 → `IntentSelector`（仿 `CompanyNameSelector` 卡片样式，紫色系）。
- 用户点击选项 → `onSendMessage("【意图选择】<技能名>")`。

#### 4.4.3 后端：意图选择前缀协议

`ChatController.chatStream` 入口处检测前缀（在 pendingSkill 判断之前）：

```java
private static final String INTENT_SELECT_PREFIX = "【意图选择】";

if (message.startsWith(INTENT_SELECT_PREFIX)) {
    String skillName = message.substring(INTENT_SELECT_PREFIX.length()).trim();
    if (skillRegistry.get(skillName) != null) {
        // 直接路由，跳过意图识别；历史消息改写为"（用户选择了技能：xxx）"
        // 参数来自上下文记忆补全（company_name/credit_code/_attachment_url）
        decision = { action: "skill", skill: skillName, params: {}, reason: "用户意图选择" };
        → handleSkill(decision, ...)
    }
}
```

要点：

- 前缀消息**不再经过 LLM 意图识别**，避免二次误判；
- 用户历史记录中保留原文，但用于上下文记忆的消息改写为 `（用户选择了技能：xxx）`，防止后续路由混淆；
- 选中技能缺失必要参数时走既有 `info_needed` 流程（如需要企业名则技能返回 info_needed，触发 pendingSkill）。

#### 4.4.4 时序

```
用户: 我想生成一份尽调报告
后端: intent_candidates 事件（generate_report / query_due_diligence_reports）
前端: 渲染 IntentSelector 卡片
用户: 点击"尽调报告生成" → 发送 "【意图选择】generate_report"
后端: 识别前缀 → 直接 handleSkill(generate_report) → 缺失参数 → info_needed
用户: 补充"小米科技" → pendingSkill 直连技能 → result 卡片
```

## 五、多意图识别（Multi-Intent Pipeline）

### 5.1 识别

多意图识别在**第三层 LLM 兜底**（无确定性候选）与**仲裁层**中完成：LLM 决策输出 `action=multi`。

```json
{
  "action": "multi",
  "skills": [
    { "skill": "query_company_basic_info", "params": { "company_name": "A公司" } },
    { "skill": "check_company_risk",       "params": { "company_name": "A公司" } }
  ],
  "reason": "用户要求先核实A公司信息，再做风险识别"
}
```

`buildMultiIntentPrompt` 判定规则（写入 system prompt）：

- 用户输入中出现**多个互不排斥的意图触发词**（如"核实信息"+"风险识别"）→ 输出 `multi`；
- 每个意图对应一个技能条目，`params` 仅放该技能独立需要的参数；
- **不拆分**无实际意义的重复项（如同一技能只出现一次）；
- 若一个意图需要前置结果（如"核实后生成尽调报告"），在 `skills` 中按依赖顺序排列，由任务规划层（第六章）复核。

### 5.2 参数共享

- 全局共享参数（`company_name` / `credit_code`）由 `ChatController.handleSkill` 的**上下文记忆补全**统一注入，每个管道任务执行前自动补充，无需 LLM 重复输出；
- 前序任务的关键输出（如核实后确认的 `credit_code`）写入上下文记忆，后续任务自动获得；
- 附件（`_attachment_url`）在管道内按需注入（如核实营业执照 → 生成报告）。

### 5.3 顺序执行与暂停恢复（pendingPipeline）

`ContextMemoryService.ConversationContext` 新增字段：

```java
/** 多意图管道剩余任务队列（List<Map<String,Object>>，每项含 skill/params/order） */
public List<Map<String, Object>> pendingPipeline = new ArrayList<>();
```

`ChatController` 新增 `handleMulti` 执行器：

```
handleMulti(decision, convId, userId, conv):
  1. plan = TaskPlanner.plan(decision.skills)          // 任务规划，见第六章
  2. 发送 planning 文本事件："我将依次为您执行：①基本信息查询 ②风险预查"
  3. 逐任务执行（复用 handleSkill 单任务逻辑，抽取为 executeSkillTask）：
       - 执行前：上下文记忆补全参数
       - 结果为 result/not_found → 更新上下文 → 执行下一任务
       - 结果含 credit_code → 写上下文，后续任务参数共享
  4. 任一任务返回 info_needed / candidates → 暂停：
       - 该任务参数存入 pendingSkillParams（复用现有机制）
       - 剩余任务队列存入 pendingPipeline
       - 结束当前事件流（不发 done 后的额外内容）
  5. 用户补充信息后（chatStream 主流程）：
       - 若 pendingPipeline 非空 → 先执行完当前任务，再顺序执行剩余任务
       - 全部完成 → 清理 pendingPipeline → 结束
```

主流程整合（`chatStream` 现有分支前插入）：

```
if (ctx.hasPendingPipeline()) {
    // 恢复管道：继续当前暂停任务 → 完成后弹栈执行剩余任务
    → handleMulti(restorePlan, ...)
} else if (ctx.hasPendingSkill()) {
    → 现有 pendingSkill 分支（重试上限 3 次逻辑不变）
} else if (message.startsWith(INTENT_SELECT_PREFIX)) {
    → 意图选择直连路由（4.4.3）
} else {
    → coordinatorService.routeIntent（三层路由）
}
```

> 注意优先级：`pendingPipeline`（多意图恢复）优先于 `pendingSkill`（单技能恢复）。单技能暂停与管道暂停互斥存在，管道恢复时内部复用 pendingSkill 字段保存当前任务状态。

### 5.4 事件流

管道内每个任务的结果事件**复用现有事件类型**（`risk_check_result` / `company_query_result` / `information_check_result` / `historical_dd_query_result` 等），前端卡片零改动即可渲染；每个任务事件附带 `_multi_index`（任务序号）与 `_plan`（规划文本）供前端展示进度。

事件序列示例（"核实A公司信息并做风险识别"）：

```
meta → text_delta("我将依次为您执行：①营业执照信息核实 ②风险预查") → text_done
    → information_check_result(核实卡片, _multi_index=1)
    → risk_check_result(风险卡片, _multi_index=2)
    → follow_up_suggestion → done
```

## 六、任务规划（Task Planning）

### 6.1 职责

任务规划层将 LLM 输出的意图集合（`skills` 数组）转换为**可执行的、有序的、带依赖与参数传递的执行计划**。规划发生在两个时机：

1. **multi 决策后处理**：`TaskPlanner.plan(skills)` 确定性生成计划；
2. **单技能执行时**：单意图视为长度为 1 的计划（`plan=[{skill}]`），规划层不干预。

### 6.2 `TaskPlanner`（新建组件）

```java
@Component
public class TaskPlanner {
    /** 输入多意图 skills 数组，输出有序执行计划 */
    public List<PlanTask> plan(List<Map<String, Object>> skills) { ... }

    /** 依赖检测：返回任务 i 是否依赖任务 j 的输出 */
    private boolean hasDependency(PlanTask i, PlanTask j) { ... }
}

public record PlanTask(String skill, Map<String, Object> params, int order,
                       String dependsOn, List<String> requiredParams) {}
```

### 6.3 排序与依赖规则

| 规则 | 说明 | 示例 |
|------|------|------|
| 用户陈述顺序优先 | 默认保持 LLM 输出的 `skills` 顺序 | "核实信息并做风险识别" → verify → risk |
| 报告依赖前置 | `generate_report` 与其他查询/核实类任务同现时，强制排到最后（报告需要前置结果作素材） | "核实A公司并生成尽调报告" → verify → generate_report |
| 历史查询不触发重排 | `query_due_diligence_reports`（历史尽调查询）不产生报告素材，与 `generate_report` 同现时保持用户陈述顺序，不执行"报告排最后" | "尽调报告生成和查询历史尽调" → generate_report → query_due_diligence_reports |
| 参数传递 | 前序任务输出 `credit_code` 后，后续任务优先使用其补全参数 | 核实后获得信用代码 → 风险预查直接使用 |
| 查询类可并行 | 无依赖的纯查询任务（如"查股东和受益人"）标记为可并行（当前实现仍顺序执行，预留并行扩展） | shareholder → beneficiary |
| 去重 | 同一技能在计划中只保留一次（合并 params） | "查下股东，顺便看下股权结构" → 单任务 shareholder |

`plan` 输出结构：

```json
{
  "plan": [
    { "skill": "verify_business_license",  "params": { "company_name": "A公司" }, "order": 1, "dependsOn": null },
    { "skill": "check_company_risk",       "params": { "company_name": "A公司" }, "order": 2, "dependsOn": "verify_business_license" },
    { "skill": "generate_report",          "params": { "company_name": "A公司" }, "order": 3, "dependsOn": "verify_business_license" }
  ]
}
```

### 6.4 规划文本（用户可见）

管道开始时发送规划提示（`_plan` 文本），使用技能中文标签，格式：

> 我将依次为您执行：① 营业执照信息核实 ② 风险预查 ③ 尽调报告生成

若某任务暂停等待补充信息，恢复时发送：

> 继续执行剩余任务：② 风险预查

## 十、验收标准与测试用例

### 10.1 单意图识别

| 用例 | 输入 | 期望决策 |
|------|------|----------|
| 确定性命中 | "帮我做一下小米科技的风险识别" | skill=check_company_risk（直接路由，LLM 只提取参数） |
| 排除词裁决 | "给小米科技的风险打分" | 命中排除词"打分" → 否决 risk → chat（或仲裁） |
| report 组冲突 | "查一下历史尽调报告" | 排除词裁决 → query_due_diligence_reports |
| 同组平票仲裁 | 构造双候选场景（如"查询海关认证和失信情况"同时命中 customs 组） | 仲裁层输出唯一技能或 clarify |
| 澄清触发 | 低置信度仲裁（confidence<0.6） | intent_candidates 事件 + 前端卡片 |
| 前缀直连 | "【意图选择】generate_report" | 跳过 LLM，直接 handleSkill |
| 兜底 | "你好" | chat |

### 10.2 多意图识别 + 任务规划

| 用例 | 输入 | 期望行为 |
|------|------|----------|
| 双意图 | "核实A公司信息并做风险识别" | multi → plan [verify, risk] → 依次执行两张卡片 |
| 报告依赖 | "核实A公司后生成尽调报告" | plan [verify, generate_report]（报告排最后） |
| 参数共享 | 第一任务返回 credit_code | 第二任务自动携带，无需用户重复输入 |
| 暂停恢复 | 管道中某任务返回 info_needed | 暂停并记录 pendingPipeline；用户补充后恢复剩余任务 |
| 去重 | "查下股东，顺便看下股权结构" | 单任务 shareholder，不重复执行 |

### 10.3 回归

- 现有 17 条规则覆盖的场景（生成报告多轮参数、附件用途询问、多轮上下文切换企业）必须保持原行为；
- `pendingSkill` 重试上限 3 次逻辑保留；
- 前端 Outreach 相关事件类型不恢复。
