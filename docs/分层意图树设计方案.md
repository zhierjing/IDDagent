## 一、背景与目标

当前意图识别第一层由 `IntentMatcher` 基于技能**扁平元数据**（`keywords` / `excludeKeywords` / `priority` / `conflictGroup`）做确定性匹配。业务侧实际定义了 20 个分支意图（branch_0 ~ branch_20），其规则天然呈**分层结构**（场景 → 对象 → 行为 → 信息类型 → 口径），扁平模型是在"压平"这棵树，导致：

- 排他关系靠**排除词互相否决**维持（海关 customs 组、report 组、"风险"与"得分"互斥），规则间耦合、难以解释；
- **AND 组合语义**无法表达（如"人行"∧"账管"、"e缴费"∧"尽调"），只能用复合词近似，分隔写法漏匹配；
- `Skill.objectType`（法人/自然人）字段存在但匹配器从未使用，无法区分自然人核实与法人核实；
- **宽松行为词**（查询词可有可无）无表达模型，仅 branch_5 强制必含查询词，其余 branch 均允许缺省。

本方案目标：将第一层确定性匹配重构为**分层意图树**，节点携带条件组（`mustAny` / `mustAll` / `mustNot`），叶子绑定技能名；保持三层路由（树匹配 → LLM 仲裁 → LLM 兜底）、多意图管道、意图穿插判定等上层机制不变。尽调业务按最新口径落地：产品尽调（branch_8）直接绑定 `generate_report`，业务子域（branch_9~12）以 `matchable=true` 预留——可正常命中但无技能绑定，命中后返回"该业务暂未开通"提示，待数据就绪后仅需绑定技能名即可零改动启用。

## 三、分层意图树设计

### 3.1 节点模型

新增 `skill/IntentNode.java`（与 `IntentCondition` 同文件或内部类）：

```java
/**
 * 意图树节点：条件满足即进入该节点；叶子节点绑定技能名。
 */
public class IntentNode {
    private final String name;                 // 节点名，如 "法人查询-风险-历史"
    private final IntentCondition condition;   // 进入条件（null = 无条件）
    private final boolean defaultLeaf;         // 兜底叶子：同父兄弟均未命中时激活
    private final boolean matchable;           // 可命中：预留节点不绑定技能（skillName=null），
                                               // 命中后由上层返回"该业务暂未开通"提示
    private final String skillName;            // 叶子绑定的技能名（matchable 预留节点为 null）
    private final String businessType;         // 扩展参数（尽调业务类型等，可为 null）
    private final List<IntentNode> children;   // 子节点（有序，匹配时全部检查）

    public boolean isLeaf() { return skillName != null || matchable; }
    // 构造/链式方法略
}

/**
 * 条件组语义：
 * - mustNot  命中任一 → 否决该节点（剪枝）
 * - mustAll  必须全部命中
 * - mustAny  命中任一即可；空列表 = 本维度宽松（不设限制，如查询行为词）
 */
public record IntentCondition(
        List<String> mustAny,
        List<String> mustAll,
        List<String> mustNot
) {
    public boolean matches(String text) {
        if (mustNot != null && mustNot.stream().anyMatch(text::contains)) return false;
        if (mustAll != null && !mustAll.stream().allMatch(text::contains)) return false;
        if (mustAny != null && !mustAny.isEmpty() && mustAny.stream().noneMatch(text::contains)) return false;
        return true;
    }
}
```

设计要点：

1. **域 = 组织分组，不设匹配门槛**：A/B/C 域本身不带条件、不做匹配裁剪；行为词（核实/查询）作为 `mustAll` 下放到每个叶子，避免"域级过滤"造成跨域误剪。C2 的 basic_info default 通过 **mustNot 全局意图词黑名单**（其他域/叶子的核心词：风险/海关/认证/失信/冻结/人行/授信/尽调/报告/历史/营业执照/核实/身份等）与其他意图互斥——黑名单词出现即放弃兜底，避免"查询/查一下"等宽松行为词无条件吞掉具体意图。
2. **defaultLeaf 表达兜底口径**：branch_3（风险最新）在 C1 内兜底——兄弟（历史/得分）均未命中时激活；branch_5（基本信息）在 C2 内兜底——兄弟（股东/受益人/族谱）均未命中时激活，且强制必含查询行为词、不含全局意图词黑名单，保证无查询词/含具体意图词时不误判。
3. **matchable 预留节点**：branch_9~12 节点 `matchable=true`、无 skillName——可正常命中（不剪枝），命中后由上层返回"该业务暂未开通"提示，而非静默落到其他技能；业务就绪后仅需绑定技能名即可零改动启用。
4. **排他性由树结构承担**：历史/得分/最新、认证/失信等互斥关系由分支结构与 defaultLeaf 表达，跨意图互斥由叶子 mustNot（branch_5 黑名单 / branch_8、branch_new 反向排除）承担，不再需要 `conflictGroup`。
5. **报告类并入尽调业务域**：generate_report（branch_8）与 query_due_diligence_reports（branch_new）挂入 A 域，互斥由 generate_report 的 `mustNot[历史,查询,查一下,查看,查找,以前,有没有,看看]` 承担；branch_new 反向排除 `[风险,海关,认证,AEO,失信]`（"风险历史"归 C1、"认证/海关"归 C3），并新增"以前/过往/有没有"时间与存在性触发词。

### 3.3 匹配算法

新建 `skill/IntentTreeMatcher.java`：

```java
public List<SkillCandidate> match(String userMessage) {
    List<SkillCandidate> leaves = new ArrayList<>();
    dfs(root, userMessage, leaves);
    return leaves; // 保持与现有 SkillCandidate 结构一致（skillName/label/matchedKeywords/score）
}

/** 深度优先：条件不满足剪枝；收集全部命中叶子；defaultLeaf 在兄弟全未命中时激活 */
private void dfs(IntentNode node, String text, List<SkillCandidate> leaves) {
    if (node.condition() != null && !node.condition().matches(text)) return;
    if (node.isLeaf()) {
        leaves.add(toCandidate(node, text));
        return;
    }
    List<IntentNode> normal = node.children().stream().filter(n -> !n.defaultLeaf()).toList();
    List<IntentNode> defaults = node.children().stream().filter(IntentNode::defaultLeaf).toList();
    int before = leaves.size();
    for (IntentNode child : normal) dfs(child, text, leaves);
    // 兄弟普通节点一个都没命中时，才激活 default 子节点
    if (leaves.size() == before) {
        for (IntentNode d : defaults) dfs(d, text, leaves);
    }
}
```

算法特征：

| 场景 | 输入示例 | 结果 |
|------|----------|------|
| 单叶子 | "云禾科技的风险" | C1 命中 → 历史/得分未中 → default 激活 → `check_company_risk` |
| 单叶子 | "查询云禾科技的信息" | C2 兄弟（股东/受益人/族谱）未中 → default 激活 → `query_company_basic_info` |
| 跨子域互斥 | "查询海关认证信息" | C3（`query_customs_auth`）命中；branch_5 被"海关/认证"黑名单否决 → 唯一路由，不再与 basic 并存 |
| 同父多口径 | "查一下风险历史得分" | `query_risk_history` + `query_risk_score` 同时命中 → LLM 仲裁 |
| matchable 命中 | "e缴费尽调怎么做" | branch_9 命中但无 skillName → 返回"该业务暂未开通"提示（chat），不静默落其他技能 |
| 无对象核实 | "核实一下" / "信息核查一下北京星河科技" | B 域兄弟（身份/执照/通讯）均未中 → branch_21 default 激活（verify_ambiguous）→ 协调层返回澄清卡片（营业执照核实/身份证核实） |
| 无叶子 | "你好" / "云禾科技"（无行为词无信息词） | 无叶子 → 第三层 LLM 完整规则兜底 → chat |
| 分隔写法 | "查一下人行账户管控情况" | 人行节点 `mustAny[人行,...,账管,账户管理,账户管控]` 中"人行"与"账户管控"分隔词各自命中 → `query_pboc_account_control`，修复复合词漏匹配；账管词单独出现同样命中 |

`match()` 返回结构复用现有 `IntentMatcher.SkillCandidate`，`matchedKeywords` 记录命中的具体关键词，供日志与仲裁 prompt 展示。matchable 预留节点命中时 `skillName` 为 null（`label` 取节点名），由上层识别为"业务未开通"候选。

## 四、与现有三层路由的融合

### 4.1 `CoordinatorService.routeIntent` 改造

```java
// 改造前（现状）
List<SkillCandidate> candidates = intentMatcher.match(userMessage);
// 改造后
List<SkillCandidate> candidates = intentTreeMatcher.match(userMessage);
```

其余流程（空候选 → LLM 兜底；唯一候选 → 参数提取；多候选 → `resolveConflict` + LLM 仲裁）**逐行不变**，仅新增 matchable 候选处理：

```
输入 userMessage
   │
   ├─ ① candidates = IntentTreeMatcher.match(userMessage)
   │     ├─ 空 → ③ LLM 完整规则兜底（buildFullRulePrompt，规则与树同步）
   │     ├─ 唯一 matchable 候选（无 skillName）→ 返回 chat："该业务暂未开通"
   │     ├─ 唯一叶子 → 直接参数提取（tryDirectParamExtraction 现状不变）
   │     └─ 多叶子 → ② LLM 仲裁（buildArbitrationPrompt 现状不变，支持 multi；
   │                   matchable 候选并入列表，仲裁不得选中其技能名）
   ▼
结构化决策（skill / chat / clarify / multi）
```

> 说明：树结构已承担层级互斥，`resolveConflict` / `findTriggeredButExcluded` 在新模型下不再需要——多叶子一律交仲裁。第一阶段保留方法签名（意图穿插处仍引用），后续清理。

### 4.2 `ChatController.classifyPipelineInput` 改造（意图穿插）

[L749](backend/src/main/java/com/IDDagent/controller/ChatController.java) 同步替换为树匹配，五级判定逻辑不变：

```java
// ② 确定性意图匹配（仅对当前消息，不含历史）
List<IntentMatcher.SkillCandidate> candidates = intentTreeMatcher.match(message);
```

`topSkill` 与 `ctx.pendingSkillName` 的比较、企业切换检测（④级）均不受影响。

### 4.3 LLM 兜底规则同步

`CoordinatorService.buildFullRulePrompt`（[L601](backend/src/main/java/com/IDDagent/service/CoordinatorService.java)）现有 17 条决策规则与树存在双重维护。本版做三件事：

1. **同步规则文案**：将规则 2~16 的触发词/排除词与树节点条件对齐（新增 branch_4/18/20 对应规则，标注"暂无数据、命中后返回 chat 或业务预留提示"；branch_1 增加角色维度、branch_8 增加"产品尽调"触发词、branch_new 移除反向排除词）；
2. **clarify 补强**：规则 1 由"意图模糊一律 chat"改为"意图不明但有多种合理解读 → 输出 clarify"（仅业务词无动作/仅查询行为词无对象/上义词无子项/核实类无核实对象四类典型场景），规则 3 对齐；规则 16 增加"能确定查询对象企业（用户输入或上下文记忆）"条件，仅行为词无企业对象（如"我想查一下"）转规则 1 输出 clarify。补强后 clarify 用例的触发路径：多候选仲裁规则 3 / 唯一候选低置信度转澄清 / LLM 兜底规则 1，测试集 14 条 clarify 用例全部保留；
3. **不自动生成**：暂不实现"从树生成 prompt"（可作后续优化项，避免本版改动面扩大）。

**补充（核实类澄清候选，方案 B）**：核实类无核实对象（如"核实一下"）的 clarify 候选允许列出未开通技能 `verify_natural_person`（身份证核实），与 `verify_business_license`（营业执照核实）并列成两张候选卡；`select_intent` 点击未注册技能时由"回退空 input 三层路由（会把 null 当消息路由成闲聊）"改为固定返回"暂未开通"提示（verify_natural_person 追加引导文案"当前可为您提供营业执照核实服务"），见 `ChatController.handleStructuredInteraction` 的 `notOpenedHint`。

## 八、已知取舍与边界

1. **branch_5 黑名单互斥取代"跨子域并存"**：基本信息 defaultLeaf 在 C2 内与兄弟（股东/受益人/族谱）互斥，跨子域/跨域互斥由 mustNot 全局意图词黑名单承担——黑名单词出现时放弃兜底（如"查询海关信息"→ 空候选 → LLM 兜底澄清；"查一下风险情况"→ 仅 check_company_risk）。代价："查一下小米科技的基本信息和风险"这类 multi 输入退化为单候选 check_company_risk（多意图需 LLM 完整规则兜底补充，当前流程唯一候选直接路由）。
2. **matchable 节点返回语义**：branch_9~12 命中 → 走"该业务暂未开通"的 chat 提示，而非静默落到其他技能；多候选仲裁时 matchable 不产出可选技能。
3. **branch_1 角色收窄待确认**：当前条件限定"法定代表人/授权代理人/财务主管"三类角色；若业务方确认保留通用自然人，移除该 mustAny 维度即可（"核实张某某的个人信息"将重新命中）。
4. **确定性优先的近似命中**：如"查云禾的冻结情况"（无"账户/账号"词）branch_16 不命中，且不含查询行为词时 branch_5 也不命中 → 无叶子走 LLM 兜底；如需更准，可后续将"仅默认分支激活"列入低置信度仲裁候选。
5. **双份维护仍存在**：树与 LLM 兜底 prompt 规则本版手工同步；"从树自动生成 prompt"列为后续优化。
6. **`resolveConflict`/`findTriggeredButExcluded` 退役**：树结构承担互斥后不再需要，本版仅停用（不删除），避免影响意图穿插引用。

## 九、后续扩展指南

新增意图（如未来新增"环境信用评价"查询）只需两步：

1. **树内加节点**：在 C 法人查询域追加叶子 `query_env_credit`（条件 `mustAny[环境,环保,绿色]`）；若存在口径区分（如历史/最新），仿照 C1 拆"普通子节点 + defaultLeaf"；
2. **注册技能**：实现并 `registry.register` 绑定技能，`IntentTree` 叶子引用同名技能名即自动生效。

预留节点启用（branch_9~12）同理：`matchable` 置 false、绑定 skillName 即可，零结构改动。若某节点需要"全部条件缺失时也可进入"（宽松行为词之外的新维度），扩展 `IntentCondition` 增加维度即可，`matches` 判定保持"空列表 = 宽松"的统一语义。
