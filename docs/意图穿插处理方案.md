## 一、背景与问题分析

### 1.1 需求描述

当用户前一个意图的规划分阶段进行时，中间有步骤完成后，用户继续询问了一个与该意图**不匹配**的其他意图。此时系统应选择该新意图进行准确处理，并在处理完成后对前一个意图进行**断点再续**，最终完成任务。

**示例**：用户提问"查询A公司历史尽调 + 生成尽调报告"（多意图管道）。查询完A公司之后（管道暂停在"报告生成/模板选择"环节），用户说"查询B公司历史尽调报告"。此时系统应先回答查询B公司的问题，回答结束后**主动询问**用户是否还需要继续前面中断的意图：用户回复"需要"→ 继续之前的意图；回复"不需要"→ 不再进行之前的意图。

### 1.2 现状分析（基于最新代码）

`ChatController.chatStream` 主流程分支顺序（L242-300）：

```
① isWaitingReport（报告生成中）        → 忽略消息，提示等待
② hasPendingPipeline（管道剩余任务）   → handleMultiResume      ← 问题点 1
③ hasPendingSkill（技能等待补充）      → 参数补全重试            ← 问题点 2
④ 【意图选择】前缀                     → 直接路由
⑤ 空消息                              → handleChat
⑥ 否则                                → routeIntent（三层路由）
```

**问题 1：管道暂停后新意图被吞**。`hasPendingPipeline=true` 时，用户的下一条消息被无条件路由到 `handleMultiResume`（L250-253），被当作对当前暂停任务的补充信息（如企业选择、附件、日期范围）处理。示例中"查询B公司历史尽调报告"会直接进入 `generate_report` 的补充流程，新意图根本没有参与三层路由的机会。

**问题 2：模板选择暂停时管道可能为空**。`generate_report` 展示模板列表（`templateStage`）时会设置 `pendingSkill` 暂停管道；若报告生成是管道的**最后一个任务**，则 `pendingPipeline` 为空（L1021-1032 只保存 `startIndex+1` 起的剩余任务）。此时用户新消息落入分支 ③（`hasPendingSkill`），同样被当作模板选择/参数补充，无法响应新意图。

**问题 3：补充信息与打断意图无判别机制**。"补充信息"（如企业候选选择 `公司：xxx\n统一信用代码：xxx`、`【模板选择】<id>`、日期范围）与"新意图"（如"查询B公司历史尽调报告"）在代码上没有任何区分，全部走恢复路径。

### 1.3 目标

1. 管道暂停期间（`hasPendingPipeline` 或 `hasPendingSkill` 存在时），用户新消息先做 **"管道补充 vs 新意图"** 判定。
2. 判定为新意图 → **全量挂起**当前管道状态 → 复用三层路由正常执行新意图（单技能/多意图/聊天均支持）。
3. 新意图执行到**稳定点**（完全结束）→ 主动询问"是否继续之前的意图"。
4. 用户确认继续 → **原样恢复**挂起管道（复用现有 `handleMultiResume` 恢复逻辑）；确认放弃 → 清理挂起状态；直接发起新问题 → 隐式放弃旧管道。

## 二、总体设计

### 2.1 核心思路：状态挂起（Suspend）与断点再续（Resume）

意图穿插的本质是**当前管道状态的全量挂起-恢复**，穿插期间旧管道与新意图的执行互不干扰：

```
[管道执行/暂停中] --用户发新意图--> [挂起旧管道] --执行新意图(三层路由)--> [新意图到达稳定点]
    --发送 interrupt_ask 询问--> [等待用户确认]
         ├─ 用户选"继续"   → [恢复旧管道]（复用 handleMultiResume）
         ├─ 用户选"不需要" → [清理挂起状态] + 确认文本
         └─ 用户发新问题   → [隐式放弃旧管道] + 执行新问题
```

### 2.2 穿插判定优先级（补充信息 vs 新意图）

| 优先级 | 判定手段 | 判定为"新意图"的条件 |
|:---:|----------|----------------------|
| 1 | 协议前缀 | `【模板选择】` → 补充；`【意图选择】` → 新意图 |
| 2 | 确定性意图匹配（`IntentMatcher.match`） | 命中候选技能 **≠** 当前暂停技能 |
| 3 | 参数合法性补充 | 消息是合法企业名 / 信用代码 / 日期 → 补充 |
| 4 | 企业切换 + 查询行为词 | 含与上下文企业不同的新企业名且带查询行为词 |
| 5 | LLM 仲裁兜底（新二分类 prompt） | LLM 判定为"新意图" |

> 判定只对**当前消息文本**做确定性匹配（`IntentMatcher.match(userMessage)` 本身不依赖历史，L33），避免把管道技能自身的历史命中当成新意图。

### 2.3 新增交互协议

| 协议 | 方向 | 说明 |
|------|------|------|
| SSE 事件 `interrupt_ask` | 后端 → 前端 | 穿插完成后询问是否继续旧管道（含剩余任务摘要） |
| 消息前缀 `【管道恢复】继续` | 前端 → 后端 | 用户选择继续旧管道 |
| 消息前缀 `【管道恢复】放弃` | 前端 → 后端 | 用户放弃旧管道 |
| 自然语言兜底 | 前端 → 后端 | `interruptAskPending` 期间手输"继续/需要/好"→ 继续；"不需要/算了/不用"→ 放弃 |

## 三、后端设计

### 3.1 上下文状态扩展（ContextMemoryService）

在 `ConversationContext`（L136-179）新增字段与配套方法：

```java
public static class ConversationContext {
    // ... 现有字段（companyName / creditCode / pendingSkillName / pendingSkillParams /
    // pendingSkillRetry / pendingInputHint / attachmentUrl / pendingPipeline / pipelinePlan / waitingReportTask）

    /** 意图穿插：被挂起的旧管道剩余任务队列（结构同 pendingPipeline） */
    public List<Map<String, Object>> suspendedPipeline = new ArrayList<>();

    /** 意图穿插：被挂起的旧管道完整计划快照（结构同 pipelinePlan，含 label/order） */
    public List<Map<String, Object>> suspendedPlan = new ArrayList<>();

    /** 意图穿插：被挂起的旧管道暂停中的任务（skill/params/hint/retry，结构同 pendingSkill） */
    public Map<String, Object> suspendedPendingSkill = null;

    /** 意图穿插：是否已发出询问、正在等待用户确认恢复 */
    public boolean interruptAskPending = false;

    /** 是否有被挂起的旧管道 */
    public boolean hasSuspendedPipeline() {
        return suspendedPipeline != null && !suspendedPipeline.isEmpty();
    }
}
```

配套方法（放在 ContextMemoryService 中，或抽到新类 `IntentInterruptService`）：

- `suspendPipeline(convId)`：把当前 `pendingSkillName/pendingSkillParams/pendingSkillRetry/pendingInputHint/pendingPipeline/pipelinePlan` 整体搬入 `suspended*` 字段，然后清空前者。
  > **关键点**：`pipelinePlan` 必须随管道一起转移。因为新意图若是多意图管道，`handleMulti` 会覆盖 `ctx.pipelinePlan`（L786），不转移将丢失旧管道完整计划，恢复时前端任务清单缩水。
- `restorePipeline(convId)`：把 `suspended*` 字段反向搬回当前管道字段，清空 `suspended*` 与 `interruptAskPending`。
- `clearSuspended(convId)`：仅清空 `suspended*` 与 `interruptAskPending`（放弃场景）。

### 3.2 主流程分支重构（chatStream）

新分支顺序（替换现有 L242-300）：

```java
if (ctx.isWaitingReport()) {
    // ① 不变：报告生成中，忽略消息
} else if (finalMessage.startsWith(PIPELINE_RESUME_PREFIX)) {

} else if (hasPendingPipeline || hasPendingSkill) {

    }
} else if (body.getMessage().startsWith(INTENT_SELECT_PREFIX)) {
    // ④ 不变
} else if (body.getMessage() == null || body.getMessage().trim().isEmpty()) {
    // ⑤ 不变
} else {
    // ⑥ 不变
}

return initEvent.concatWith(mainFlow)
        .concatWith(Flux.defer(() -> interruptAskCheck(convId, finalConv)))  // 新增：流尾统一检查
        ...;
```

### 3.3 穿插判定算法（classifyPipelineInput）

新方法（可置于 ChatController 或抽到 IntentInterruptService，注入 `IntentMatcher`/`SkillRegistry`）：

```java
/** 管道暂停期间用户消息的归类 */
enum InputClass { PIPELINE_SUPPLEMENT, NEW_INTENT }

private InputClass classifyPipelineInput(ConversationContext ctx, String message) {
    // ① 协议前缀
    if (message.startsWith(TEMPLATE_SELECT_PREFIX)) return PIPELINE_SUPPLEMENT; // 模板选择
    if (message.startsWith(INTENT_SELECT_PREFIX)) return NEW_INTENT;            // 明确选择新技能
    if (message.equals("以上都不是")) return PIPELINE_SUPPLEMENT;                // 企业候选否决

    // ② 确定性意图匹配（仅对当前消息，不含历史）
    List<IntentMatcher.SkillCandidate> candidates = intentMatcher.match(message);
    if (!candidates.isEmpty()) {
        String topSkill = candidates.get(0).skillName();
        if (!topSkill.equals(ctx.pendingSkillName)) {
            return NEW_INTENT;  // 命中与暂停技能不同的技能 → 新意图（如"查询B公司历史尽调"→ query_due_diligence_reports）
        }
        // 命中与暂停技能相同：若消息携带与上下文不同的企业名，视为"切换查询对象的新意图"，
        // 否则视为补充信息（如 query_due_diligence_reports 缺日期时用户回复日期区间）
        if (containsNewCompany(message, ctx)) return NEW_INTENT;
        return PIPELINE_SUPPLEMENT;
    }

    // ③ 参数合法性补充：企业候选选择（公司：xxx\n统一信用代码：xxx）、企业名、信用代码、日期
    if (looksLikeCompanySelection(message) || CompanyNameExtractor.isValidCompanyName(message)
            || CompanyNameExtractor.isValidCreditCode(message) || looksLikeDateRange(message)) {
        return PIPELINE_SUPPLEMENT;
    }

    // ④ 企业切换 + 查询行为词（如"帮我查一下 云禾科技"）
    if (containsNewCompany(message, ctx) && containsQueryVerb(message)) {
        return NEW_INTENT;
    }

    // ⑤ LLM 仲裁兜底（见 3.7：CoordinatorService.classifyIntentInterrupt）
    return coordinatorService.classifyIntentInterrupt(message, ctx.pendingSkillName,
            ctx.pendingSkillParams, ctx.pendingInputHint);
}
```

**判定正确性论证（对齐示例）**：
- 管道 = [查询A公司历史尽调 → 生成尽调报告]，暂停于 `generate_report` 模板选择，`pendingSkillName=generate_report`，`pendingPipeline` 可能为空。
- 用户消息"查询B公司历史尽调报告"：不匹配任何前缀；`IntentMatcher.match` 命中 `query_due_diligence_reports`（关键词"历史/查询/报告"），`topSkill ≠ generate_report` → **NEW_INTENT** ✓
- 用户点击企业候选"公司：B公司\n统一信用代码：xxx"：不命中技能候选 → 第 ③ 步 `looksLikeCompanySelection` → **PIPELINE_SUPPLEMENT** ✓
- 用户回复"今年 1 月到 3 月"（补充 query_due_diligence_reports 的日期范围）：不命中技能候选，第 ③ 步 `looksLikeDateRange` → **PIPELINE_SUPPLEMENT** ✓
- 用户回复"以上都不是"：第 ① 步 → **PIPELINE_SUPPLEMENT** ✓

### 3.4 穿插处理（handleInterrupt）

```java
private Flux<String> handleInterrupt(String convId, String userId, Conversation conv, String userMessage) {
    ContextMemoryService.ConversationContext ctx = contextMemoryService.get(convId);
    // 1. 全量挂起旧管道（含 pendingSkill 与 pipelinePlan 快照）
    contextMemoryService.suspendPipeline(convId);
    log.info("Pipeline suspended for interrupt, conv: {}", convId);

    // 2. 执行新意图（完整复用三层路由；新意图若是多意图管道，
    //    其 handleMulti/handleMultiResume 正常工作，互不干扰）
    return coordinatorService.routeIntent(userMessage, conv.getMessages(), convId)
            .flatMapMany(decision -> dispatchDecision(decision, convId, userId, conv, userMessage));
}
```

> 恢复旧管道的时机不由 `handleInterrupt` 负责，而是统一由流尾的 `interruptAskCheck` 判定——见 3.5。

### 3.5 断点询问（interruptAskCheck，流尾统一检查）

在 `chatStream` 返回流的尾部统一挂一个检查（见 3.2 代码），**一次接入覆盖所有"新意图到达稳定点"的路径**：

```java
private Flux<String> interruptAskCheck(String convId, Conversation conv) {
    return Flux.defer(() -> {
        ContextMemoryService.ConversationContext ctx = contextMemoryService.get(convId);
        // 有挂起的旧管道，且新意图完全结束（无任何活动中的管道/技能/报告等待）→ 询问
        if (ctx.hasSuspendedPipeline()
                && !ctx.hasPendingSkill() && !ctx.hasPendingPipeline() && !ctx.isWaitingReport()) {
            ctx.interruptAskPending = true;
            Map<String, Object> data = new LinkedHashMap<>();
            data.put("message", "您之前还有 " + ctx.suspendedPlan.size() + " 项任务未完成，是否继续执行？");
            data.put("plan_summary", ctx.suspendedPlan);   // 剩余任务摘要 [{skill,label,order},...]
            data.put("total", ctx.suspendedPlan.size());
            return Flux.just(sseEvent("interrupt_ask", data, null, convId));
        }
        return Flux.empty();
    });
}
```

覆盖的稳定点（无需逐点埋检查逻辑）：
- 穿插的**单技能**执行完成（`result`/`task_done`）→ 本次流尾触发询问
- 穿插的**多意图管道**全部执行完（`executePipeline` 尾）→ 本次流尾触发询问
- 穿插的**纯聊天**回答完 → 本次流尾触发询问
- 穿插管道中途暂停（`pipeline_paused`）→ 本次流尾检查不满足（有 pending），不询问；后续用户每轮补齐直到管道最终结束的那一轮，流尾自动触发询问

### 3.6 断点再续（handleInterruptAnswer）

```java
private Flux<String> handleInterruptAnswer(String convId, String userId, Conversation conv, String message) {
    ContextMemoryService.ConversationContext ctx = contextMemoryService.get(convId);
    String answer = message.substring(PIPELINE_RESUME_PREFIX.length()).trim();

    if (PIPELINE_RESUME_YES.equals(answer)) {
        // ① 继续：恢复挂起状态 → 复用现有 handleMultiResume（其内部已处理：
        //    先完成暂停任务 pendingSkill，再执行剩余任务 pendingPipeline；
        //    planning resume=true + task_start 事件重建前端任务清单）
        contextMemoryService.restorePipeline(convId);
        log.info("Pipeline restored after interrupt, conv: {}", convId);
        if (ctx.hasPendingSkill() || ctx.hasPendingPipeline()) {
            return handleMultiResume(convId, userId, conv, "");
        }
        return Flux.empty();
    }
    // ② 放弃：清理挂起状态 + 确认文本
    contextMemoryService.clearSuspended(convId);
    return Flux.just(sseEvent("text_delta", Map.of("content", "好的，已取消之前的任务"), null, convId),
                     sseEvent("text_done", Map.of("content", "好的，已取消之前的任务"), null, convId));
}
```

### 4.1 类型与事件扩展（types/index.ts）

```ts
/** 意图穿插询问数据 */
```

### 4.3 事件处理（useChat.ts / ChatMessage.tsx）

- `useChat.ts` 新增 `case 'interrupt_ask'`：作为一条可见 assistant 卡片消息（`extra.action='interrupt_ask'`）插入对话流，并**持久化**（后端或前端落盘，使切换会话/刷新后询问卡片仍可点击）。
- `ChatMessage.tsx`：按 `extra.action === 'interrupt_ask'` 路由渲染 `InterruptAskCard`。
- `sendMessage` 正常发送即可（【管道恢复】前缀按普通消息发送，后端主流程解析）。

### 4.4 planning resume 增强（重要）

**问题**：穿插恢复时，对话流中最后一张 `pipeline` 卡是**新意图的管道卡**（已完成）。现有 `useChat.ts` 对 `resume=true` 的 planning 事件是"更新最后一张 pipeline 卡"（L257-278）——会错误更新新管道卡。

**方案**：恢复路径的 planning 事件（`handleMultiResume` 发出）携带完整 `plan`，前端 resume 处理改为**优先按 plan 内容匹配历史卡**：

```ts
if (data.resume) {
  // 优先匹配：plan 的 skill 序列与历史某张 pipeline 卡一致（意图穿插恢复场景）
  const targetIdx = next.findLastIndex((m) => {
    const ex = m.extra;
    return ex?.action === 'pipeline'
      && (ex.plan?.map(p => p.skill).join(',') === data.plan.map(p => p.skill).join(','));
  });
  // 回退：找不到匹配卡（普通暂停恢复）→ 更新最后一张 pipeline 卡（现有逻辑）
  const idx = targetIdx !== -1 ? targetIdx : /* 现有最后一张逻辑 */;
  ...
}
```

> 普通暂停恢复（无穿插）时，恢复的 plan 与最后一张卡相同，两种策略结果一致，不影响现有行为。

## 五、完整时序示例

以需求示例为蓝本（管道 = [查询A公司历史尽调, 生成尽调报告]）：

```
用户：查询A公司历史尽调和生成尽调报告
  → routeIntent → action=multi → handleMulti → planning(plan=2项, resume=false)
  → task_start(1/2, query_due_diligence_reports)
  → historical_dd_query_result（A公司历史尽调结果卡）
  → task_start(2/2, generate_report)
  → report_generate_result（模板列表 stage=templates）→ setPendingSkill(generate_report)
  → pipeline_paused（pendingPipeline 为空，报告为最后任务；或含后续剩余任务）

用户：查询B公司历史尽调报告
  → 主流程分支③：hasPendingSkill=true，无穿插 → classifyPipelineInput
  → IntentMatcher 命中 query_due_diligence_reports ≠ generate_report → NEW_INTENT
  → handleInterrupt：suspendPipeline（挂起 generate_report 模板选择状态 + pipelinePlan）
  → routeIntent → skill(query_due_diligence_reports, 公司=B) → B 公司结果卡
  → 流尾 interruptAskCheck：suspended 非空 + 无 pending → interruptAskPending=true
  → 发送 interrupt_ask："您之前还有 1 项任务未完成（生成尽调报告），是否继续执行？"
  → 前端渲染 InterruptAskCard

用户点击「继续执行」→ 前端发送"【管道恢复】继续"
  → 主流程分支②：handleInterruptAnswer → restorePipeline（恢复 generate_report 模板选择）
  → handleMultiResume → planning(resume=true, 旧管道 plan) + task_start(2/2)
  → 前端 resume 增强：按 plan 内容匹配到旧管道 plan 卡更新
  → report_generate_result（模板列表重新展示）→ 用户选模板 →【模板选择】→ 报告生成
  → task_done → executePipeline 完成 → complete 卡（"2 项任务已完成"闭环）
  → 流尾 interruptAskCheck：suspended 已清空 → 不询问 ✓

（分支场景）用户点击「不需要」→ 发送"【管道恢复】放弃"
  → clearSuspended → 文本"好的，已取消之前的任务" → 旧管道 plan 卡保留历史暂停状态
```

## 六、边界情况

| # | 场景 | 处理策略 |
|---|------|----------|
| 1 | 穿插的新意图本身是多意图管道且中途暂停 | 新管道正常走 `pendingPipeline/pendingSkill` 恢复；旧管道保持挂起，待新管道完全结束后流尾才发询问 |
| 2 | 穿插嵌套（新意图执行中用户又发无关意图） | v2 已支持（挂起栈）：`suspended*` 单字段升级为 `Deque<Map> suspendedStack`（LIFO），每次穿插将当前活动状态（pipeline/plan/pendingSkill）打包为快照压栈，恢复/放弃时从栈顶弹出。主流程已穿插状态不再跳过判定——当前管道暂停时统一走 `classifyPipelineInput`，判为新意图则继续压栈（嵌套）。恢复语义：只作用于栈顶一层，继续→弹出恢复；放弃→丢弃栈顶，若栈仍有下一层则立即发下一张询问卡（逐层决定）；直接发新问题→清空整个栈（隐式放弃全部） |
| 3 | 等待报告期间（`isWaitingReport`） | v3 已支持穿插：报告生成中的消息不再忽略——一律视为穿插新意图（报告生成中无参数可补充），`suspendPipeline` 快照含 `waitingReport` 并清空活动状态后压栈，再执行新意图；报告完成后由 `report-completed` 推进，穿插期间报告先完成则置 `pendingReportDone` 标记，恢复该挂起层时消费并就地推进（防止推进动作丢失导致管道死锁）。例外：带【管道恢复】前缀的消息（历史询问卡点击）提示等待——报告等待期间栈顶可能仍为更早挂起层，恢复会与等待中的报告冲突。已知限制：多层含 `waitingReport` 快照时 `report-completed` 仅能按单 `pendingReportDone` 标记尽力而为（无法区分嵌套报告），恢复时按栈序就近推进 |
| 4 | 后端重启 | `suspended*` 为内存态，重启后丢失 → 旧管道隐式放弃（与现有 `pendingPipeline/pipelinePlan` 内存态处理一致）。增强项：将挂起快照持久化为 assistant 消息（复用 `persistPipelineCard` 模式），重启后从历史恢复 |
| 5 | 判定误判 | 三级防线：确定性匹配（可测试）→ 参数合法性补充（企业名/信用代码/日期/候选选择）→ LLM 仲裁兜底；且"补充信息"误判为"新意图"的后果仅是多一次询问（用户可选放弃），危害可控 |
| 6 | 穿插后用户不回答、直接发新问题 | 隐式放弃旧管道，正常执行新问题（3.6 自然语言兜底） |
| 7 | 前端刷新/切换会话 | `interrupt_ask` 卡片需持久化（assistant 消息带 extra），恢复后仍可点击；点击发送【管道恢复】前缀，后端按状态处理（若后端已重启丢失挂起态，前缀消息自然落到 routeIntent 兜底） |
| 8 | 恢复时旧管道任务参数 | 挂起时 `pendingSkillParams` 与 `pipelinePlan` 全量保留，恢复后继续用旧参数（A公司），与新意图（B公司）互不污染；`ctx.companyName/creditCode` 在新意图执行时会被更新为 B，恢复后 `handleMultiResume` 的上下文补全（`sameCompany` 判断）不会用 B 覆盖旧管道已显式携带的 A 参数 |
| 9 | `interrupt_ask` 重复触发 | 询问仅由流尾检查触发一次；`interruptAskPending=true` 期间不会再穿插（分支③ 判定前已拦截），无重复询问风险 |
