# 意图识别 · 任务规划 · 意图穿插 技术解析（面试复习版）

> 适用项目：IDDagent 智能尽调助手（Spring Boot WebFlux 后端 + React/TS 前端）
> 定位：把设计文档与最新代码融合成一份"能讲清楚设计动机、方案权衡、实现细节"的面试复习材料。
> 核心类：`CoordinatorService` / `IntentTreeMatcher` / `IntentTree` / `IntentNode` / `TaskPlanner` / `ChatController` / `ContextMemoryService` / `IntentInterruptClassifier` / `PlanProjectionService` / `ExecutionFrame`
> 版本：已同步意图穿插融合改造（Phase 1~7：frameId / ExecutionFrame / Plan 状态投影 / 六层分类器 / 结构化协议 / 交互 ID 化 / DeferredEvent）

## 一、系统全景：一条用户消息的完整旅程

```
用户消息
  │
  ▼
① 主流程分支裁决（ChatController.chatStream）        ← 状态机入口（顺序即优先级）
  │  结构化恢复协议（resume_frame/abandon_frame）→ 帧校验后恢复/放弃
  │  结构化交互协议（select_candidate/select_intent/select_template）→ 帧归属校验后转发
  │  "以上都不是" → 候选否决兜底（保留 pendingSkill 待重新输入企业名）
  │  报告生成中 → 穿插新意图 / 【管道恢复】前缀提示等待
  │  【管道恢复】前缀 → 显式回答"是否继续旧管道"
  │  interruptAskPending（询问已发出）→ 自然语言兜底（继续/放弃/新问题）
  │  管道暂停中 → 六层判定"补充信息 vs 新意图"（意图穿插）
  │  【意图选择】前缀 → 直连路由，跳过 LLM
  │  其他       → 进入三层意图路由
  ▼
② 三层意图路由（CoordinatorService.routeIntent）      ← 意图识别
  │  第①层 分层意图树确定性匹配（零 LLM，毫秒级）
  │        ├─ 唯一候选 → 直接参数提取（零 LLM）/ LLM 仅提取参数
  │        ├─ 核实对象不明（verify_ambiguous）→ 核实澄清卡
  │        └─ 多候选 → 第②层 LLM 仲裁
  │  第②层 LLM 仲裁（多候选时）
  │  第③层 LLM 完整规则兜底（空候选时）
  ▼
③ 结构化决策（action: skill | chat | clarify | multi | preset_reply）
  ▼
④ 任务规划（TaskPlanner）                             ← 任务规划
  │  multi → 有序执行计划 plan（去重 / 排序 / 依赖）
  │  skill → 长度 1 的 plan
  ▼
⑤ 技能执行管道（executePipeline）                     ← 执行 + 状态挂起
  │  逐任务执行，上下文记忆补全参数
  │  任一任务 info_needed/candidates/模板选择 → 暂停，pendingPipeline 记录剩余任务
  │  generate_report → 跳转 H5 异步生成，waitingReportTask 挂起等待
  │  Plan 状态单向投影（PlanProjectionService）：步骤 RUNNING→WAITING→DONE
  ▼
⑥ SSE 事件流 → 前端卡片渲染（结果卡 / 任务清单卡 / 澄清卡 / 询问卡 / 交互卡）
  │  frameId 贯穿所有事件与卡片（一个独立意图 = 一个 frameId）
  ▼
⑦ 流尾 interruptAskCheck → 挂起栈非空且当前意图结束 → 询问"是否继续旧管道"
```

**一句话总结**：意图识别回答"用户要做什么"，任务规划回答"按什么顺序做"，意图穿插回答"做一半时用户换需求了怎么办"，Plan 投影回答"每步任务现在是什么状态"。

## 二、意图识别：三层架构

### 2.1 为什么不是"全 LLM 一把梭"？（设计动机）

最早系统用单层 LLM + 17 条硬编码规则做意图路由，痛点：

| 问题 | 表现 |
|------|------|
| 不可解释 | 同一句话在不同上下文可能路由到不同技能，无法测试 |
| 冲突无仲裁 | 相似技能（生成报告 vs 历史查询）靠 prompt 硬碰硬 |
| 无澄清能力 | 意图模糊时只能降级为闲聊 chat |
| 成本与延迟 | 每轮都调 LLM |

**核心设计原则：确定性优先——能确定性判断的绝不让 LLM 决策。** LLM 只做"选"不做"猜"：有候选时只仲裁/提取参数，无候选时才完整规则兜底；穿插判定前四级零 LLM。

### 2.2 第①层：分层意图树确定性匹配（零 LLM）

#### 树结构：四域组织

```
ROOT
├── A 尽调业务域
│   ├── branch_8  产品尽调生成 → generate_report（mustNot 承担与历史查询互斥）
│   ├── branch_new 历史尽调报告查询 → query_due_diligence_reports
│   └── branch_9~12 matchable 预留：e缴费/银企互联/融e聚/财智账户卡尽调
├── B 核实域
│   ├── branch_1  身份核实 → verify_natural_person（预留）
│   ├── branch_2  营业执照核实 → verify_business_license
│   ├── branch_20 通讯核实 → verify_contact_info（预留）
│   └── branch_21 无对象核实（defaultLeaf 兜底）→ 虚拟技能 verify_ambiguous → 澄清卡
└── C 法人查询域
    ├── C1 风险子域：历史风险 / 风险得分 / ★最新风险(defaultLeaf 兜底)
    ├── C2 工商子域：股东 / 受益人 / 企业族谱 / ★基本信息名词对象 / ★基本信息(defaultLeaf + 全局意图词黑名单)
    ├── C3 海关子域：海关认证 / 海关失信（互斥由分支结构承担）
    └── 独立叶子：账户冻结 / 人行账户管控 / 授信信息
```

关键设计决策：

1. **域 = 纯组织分组，不设匹配门槛**。行为词（查询/核实）下放到叶子条件，避免"域级过滤"跨域误剪。如"查风险"必须命中 C1 叶子，而不是先过"C 法人查询域"的门槛。
2. **互斥由树结构承担**，不再需要 `conflictGroup` 字段。历史/得分/最新三选一由 defaultLeaf 表达；认证/失信互斥由各叶子 mustAny 维度承担；跨意图互斥（如 generate_report vs 历史查询）由叶子 `mustNot` 反向排除承担。
3. **defaultLeaf 兜底 + 防劫持**：同父兄弟全未命中时才激活默认叶子；且默认叶子带**全局意图词黑名单**（mustNot 包含其他域/叶子的核心词），防止"查询/查一下"这类宽松行为词无条件吞掉具体意图（如"查一下风险"不会被基本信息兜底抢走）。
4. **matchable 预留节点**：branch_9~12 标记 `matchable=true`、不绑定技能名（skillName=null），可正常命中但不剪枝；命中后上层返回「该业务暂未开通」固定文案（preset_reply，不调 LLM），**不静默落到其他技能**。业务就绪后只需绑定技能名即可零改动启用——这是"为未来扩展预留"的设计。
5. **预留叶子 = 树已建但技能未注册**（如 verify_natural_person / verify_contact_info / query_risk_history / query_risk_score）：命中同样返回"未开通"提示，与 matchable 语义一致。
6. **无对象核实兜底（branch_21）**：仅"核实/核验/核查/核对"类行为词且未指明核实对象时激活（如"核实一下"、"上传的附件帮我核实一下"），绑定虚拟技能 `verify_ambiguous`（非真实技能）。命中后由 CoordinatorService 构造 clarify 决策（营业执照核实/身份证核实候选卡），与 LLM 兜底规则同语义——核实对象不明不硬猜，让用户选。
7. **C2 基本信息双叶子**：行为词兜底（branch_5，defaultLeaf 强制必含查询行为词）+ 名词对象直击（branch_5n 普通叶子："工商信息/注册资本/营业执照信息"等直接命中 basic，无需查询词）；同技能多叶子命中只保留 score 最高一条，避免双候选进仲裁。

#### 匹配算法：DFS + 条件组

```
IntentTreeMatcher.match(message):
  dfs(root, message, leaves)
  ├─ 节点条件不满足 → 剪枝返回
  ├─ 叶子 → 收集为 SkillCandidate
  └─ 组节点 → 先遍历普通子节点
             若普通子节点全未命中 → 才激活 defaultLeaf 子节点
  leaves 按 score 降序（score = 命中词数*10 + 最长命中词长度，仅用于排序展示）
  同技能多叶子命中只保留 score 最高一条（matchable 候选不去重——不同预留业务互不相同）
```

条件组语义（`IntentCondition`）：

| 字段 | 语义 |
|------|------|
| `mustAll` | 必须全部命中（如基本信息的查询行为词） |
| `mustAny` | 任一命中即满足；空列表 = 本维度宽松（如纯业务词叶子） |
| `mustNot` | 任一命中即否决（如 generate_report 排除"历史/查询"） |
| `extraMustAnyGroups` | 附加维度组，每组任中其一、组间 AND（如"营业执照"+"核实/核对/核验"两个维度都满足才命中） |

#### 唯一候选的确定性执行路径（重要优化）

树匹配唯一命中且为可执行技能时，**优先直接提取参数、跳过 LLM**（`tryDirectParamExtraction`）：

```
1. credit_code：统一信用代码字段 / 18 位裸代码（CompanyNameExtractor.extractCreditCode）
2. company_name：统一公共清洗链（extractCompanyName，剔除查询对象词/动作词）
3. 消息未含企业名 + 上下文引用词（"这家/该公司"）→ 上下文记忆补全
4. 全部失败 → 回退 LLM 参数提取（不硬凑）
```

提取成功 → `action=skill` + confidence 0.95 + "确定性匹配 + 直接参数提取" reason，**整条链路零 LLM 调用**。提取失败 → 才回退 LLM 参数提取 prompt。

### 2.3 第②层：LLM 仲裁（多候选时）

候选数 > 1 时，`buildArbitrationPrompt` 把候选列表 + 用户输入 + 对话历史交给 LLM，裁决为：

- **单技能**（输出 skill + confidence + alternatives + reason）
- **multi**（多意图管道，输出 skills 数组）
- **clarify**（LLM 显式要求澄清）
- **chat**（降级聊天）

要点：

- **置信度阈值 0.6**：仲裁置信度 < 0.6 → 后端自动改写为 clarify 决策（发送 `intent_candidates` 澄清卡）；≥ 0.6 正常路由。
- **parseResponse 决策归一化（防幻觉）**：LLM 直接将技能名作为 action 输出 → 强制改写为 `{action:skill}`；输出注册表之外的技能名 → fallback chat（degraded 标记，触发模型级联升级重判）。
- **matchable 候选并入仲裁列表**：仅供 LLM 理解语境，仲裁不得选中其技能名（无 skillName 可输出）。
- **被排除词否决但触发词命中的技能（excludedTriggers）**：并入仲裁 prompt 的补充段落，提示 LLM 判断用户是否同时表达了这些意图（如"查X风险和信息"含风险与基本信息两个意图 → 输出 multi）。
- **确定性优先原则的延伸**：多候选直接交仲裁，不再触发"低置信度必澄清"的简单策略——只有当 LLM 自己也拿不准（低置信度）时才转澄清。

### 2.4 第③层：LLM 完整规则兜底（空候选时）

树匹配零命中 → `buildFullRulePrompt`（19 条决策规则，与树手工同步）做完整判断：

- 规则化的意图判定（如"含风险+历史 → query_risk_history 未开通提示"）
- **多意图检测**（多个互不排斥的触发词 → action=multi）
- 上下文记忆规则（"换一家"→ 匹配最近同类型技能；"再查2024年的"→ 变更查询条件）
- 核实类无对象的澄清可列出两个候选（verify_business_license 已注册 + verify_natural_person 未开通但允许列出）
- 模糊输入（意图不明确但多种合理解读）→ clarify，而非 chat

### 2.5 模型级联（成本优化）

```
callLLM(prompt):
  ① light 模型（便宜快）按当前 prompt 决策
  ② 需要升级（shouldEscalate）→ 主模型用完整规则 prompt 重判
  ③ 升级结果直接返回，不再递归
```

- **shouldEscalate 规则**：skill 置信度 < 0.6 → 升级；clarify / multi → 升级（复杂场景主模型更可靠）；chat → 仅解析失败兜底（degraded）才升级；未知 action → 升级。
- **调用失败不升级**：主模型大概率同样失败，直接 fallback chat。
- 参数提取、仲裁、兜底共用此级联，但**升级时统一改用完整规则 prompt**——轻量任务 cheap 模型搞定，疑难任务主模型兜底。
- 历史消息限最近 8 条、单条截断 500 字、结构化卡片内容替换为占位符——控制 token 成本与噪声。

### 2.6 意图澄清交互闭环（Phase 6 升级版）

触发：仲裁低置信度（<0.6）、LLM 显式 clarify、核实对象不明（verify_ambiguous）。

```
后端：intent_candidates 事件 {message, candidates, user_input, frameId, interactionId}
  ├─ user_input：原始用户输入随卡持久化——点击后据此恢复技能参数（如企业名），
  │   避免参数丢失被上下文自动填充成上一轮企业（如"核实星河信息"被误填成小米科技）
  ├─ frameId：所属任务帧（无活动任务时为澄清卡分配新帧）
  └─ interactionId：交互卡唯一标识（一次交互一个 ID，随事件下发、点击回传）
前端：IntentSelector 卡片（用户点击选项）
  ├─ 新协议：发送结构化 JSON {"action":"select_intent","frameId":"Fxxx","interactionId":"Ixxx","skill":"<技能名>"}
  │   后端校验 frameId == 当前活动帧（旧卡点击 → INTERACTION_SUSPENDED 拒绝）
  │   校验通过 → 从澄清卡恢复 user_input → LLM 提取参数 → 直接 handleSkill（跳过 LLM 意图识别）
  └─ 旧协议：发送 "【意图选择】<技能名>"（无帧信息时从最近一张澄清卡恢复原始输入）
后端：未注册技能（如 verify_natural_person）点击 → 返回"暂未开通"引导文案，不回退路由
```

协议的价值：**用户的选择是最高置信度的意图，不再让 LLM 二次误判**；interactionId + frameId 让"哪张卡属于哪个任务"可精确定位，旧卡点击不会污染当前任务。

## 三、任务规划：Multi-Intent Pipeline

### 3.1 识别多意图

多意图识别发生在**仲裁层与 LLM 兜底层**：LLM 决策输出 `action=multi` + `skills` 数组（每项含 skill/params，按依赖顺序排列）。判定规则：多个互不排斥的意图触发词、不拆分重复项。

### 3.2 TaskPlanner：确定性规划（LLM 只输出集合，排序交给代码）

`TaskPlanner.plan(skills)` 的确定性规则：

| 规则 | 实现 |
|------|------|
| **去重** | LinkedHashMap 按技能名去重，保留首次出现的 params（合并） |
| **技能合法性过滤** | 未注册技能直接跳过（防御 LLM 幻觉） |
| **报告依赖前置** | `generate_report` 与素材来源类技能同现时强制排最后（报告需要前置结果作素材） |
| **例外不重排** | `query_due_diligence_reports` 不产生报告素材，与报告同现时保持用户陈述顺序 |
| **参数传递** | 前序任务输出 credit_code → 后续任务上下文补全自动使用 |
| **依赖标注** | 报告任务 dependsOn = 前一个任务；通用共享参数 company_name/credit_code |

**为什么排序不用 LLM？** 排序是确定性规则（报告必须在查询后），用代码保证可测试、可解释；LLM 只负责"识别出有哪些意图"，"怎么排"交给确定性层——与三层路由的"确定性优先"一脉相承。

### 3.3 执行管道：planning → task_start → 结果卡 + Plan 状态投影

```
handleMulti(decision):
  1. plan = taskPlanner.plan(skills)
  2. 分配/复用 frameId（一个独立意图 = 一个 frameId）
  3. PlanProjectionService.createPlan → PlanRuntime（步骤全 PENDING，状态视图）
  4. 持久化任务清单卡（kind='plan'，作为 assistant 消息落盘，刷新不丢）
  5. 发 planning 事件（plan 快照 + frameId + "我将依次为您执行：①xx ②xx"）
  6. executePipeline 逐任务执行：
     - task_start 事件（index/total/order/frameId；total 取完整计划数，防 resume 缩水）
     - 上下文记忆补全参数（company_name / credit_code / _attachment_url，独立补全互不连坐）
     - 结果事件复用单技能事件类型（risk_check_result 等，前端卡片零改动）
     - 任务完成 → task_done + Plan 步骤 DONE
     - 管道全部完成 → 持久化完成卡（kind='complete'）+ 历史卡标记 completed + Plan COMPLETED
```

**Plan 状态投影（Phase 3）——只记录状态，不参与调度**：

```
PlanProjectionService（Pipeline execution → Plan state projection，单向）
  ├─ createPlan(convId, frameId, planSnapshot)   → PLAN_CREATED（步骤全 PENDING）
  ├─ markStepRunning(order)                      → 步骤 RUNNING + 计划 RUNNING
  ├─ markStepWaitingInput(order)                 → info_needed/候选/模板选择 → WAITING_INPUT
  ├─ markStepWaitingExternal(order)              → 报告跳转 H5 → WAITING_EXTERNAL
  ├─ markStepDone(order)                         → task_done → DONE
  ├─ markPlanCompleted()                         → 管道全部完成 → COMPLETED
  └─ markPlanAbandoned()                         → 挂起层被放弃 → ABANDONED
```

- **PlanRuntime**：planId（"P_"+UUID）、frameId、steps、currentStepIndex、整体 PlanStatus（PENDING/RUNNING/WAITING_INPUT/WAITING_EXTERNAL/COMPLETED/FAILED/ABANDONED）。
- **PlanStep**：stepId、skillName、title、order、步骤 PlanStepStatus（PENDING/RUNNING/WAITING_INPUT/WAITING_EXTERNAL/DONE/FAILED）、statusMessage。
- 投影方向严格单向：**禁止 Plan 反过来决定 Pipeline 执行什么**；单技能独立执行无 PlanRuntime，投影方法静默跳过。
- 挂起时 PlanRuntime 随 ExecutionFrame 快照保存（穿插期间新意图的计划不覆盖旧计划），恢复时还原；后端重启丢失后 `ensurePlan` 按历史快照重建。

### 3.4 暂停-恢复：pendingSkill + pendingPipeline

任一任务返回 `info_needed`（缺参数）/ `candidates`（企业模糊候选）/ 模板选择（stage=templates）→ 管道暂停：

- 当前任务参数 → `pendingSkillParams`（复用单技能暂停机制）
- **剩余任务队列 → `pendingPipeline`**（List<Map>，每项含 skill/params/order/_index）
- 发送 `pipeline_paused` 事件（前端任务清单卡标记 paused + waitingConfirm，hint 去重展示）
- Plan 步骤投影 WAITING_INPUT

用户补充信息后，主流程检测 `hasPendingPipeline` → `handleMultiResume`：

```
先完成当前暂停任务（pendingSkill 重入，带 _user_input）
→ 弹栈执行 pendingPipeline 剩余任务（续跑前用最新上下文企业刷新剩余任务参数，
  防止旧快照简称再次模糊匹配弹候选卡）
→ 全部完成 → 清理 pendingPipeline → planning(resume=true) 更新任务清单卡
→ 恢复的任务再次缺参 → 停止续跑，保留剩余队列，等待下一条消息
```

**优先级：`pendingPipeline` 恢复 > `pendingSkill` 恢复**——多意图暂停内部复用 pendingSkill 字段保存当前任务，二者是"管道 + 管道内当前位置"的关系。

### 3.5 报告异步生成的特殊挂起

`generate_report` 与普通查询技能不同：用户跳转 H5 编辑页、上传附件后报告**异步生成**。管道挂起方式：

- `waitingReportTask` 记录等待中的报告任务（含 skill/label/order/frameId/模板信息）
- 前端轮询报告状态（`/active`、`/pending` 双 3s 轮询 + 切换会话立即注入），完成后调 `/chat/report-completed` 推进管道：
  - 报告是**最后一个任务** → 持久化完成卡 + 清理计划快照（allDone=true）+ Plan COMPLETED
  - 报告是**中间任务** → 把 pendingPipeline 首项升级为 pendingSkill，用户下条消息续跑
- **穿插期间报告完成** → 报告等待任务随帧挂起，report-completed 无法就地推进 → `pendingReportDone` 标记（兼容布尔）+ Phase 7 DeferredEvent 事件入帧，恢复该挂起层时消费后就地推进

**轮询去重（双保险，防日志刷屏）**：

- **前端**：`processedReportIdsRef`（Set<reportId>）——/active 与 /pending 两个轮询都会对 completed 报告调推进接口，按 reportId 去重只调一次；接口有效响应（推进/跳过/推迟）即记入已消费集合。
- **后端**：`markReportConsumed`（consumed 标记）——有效处理后的报告不再出现在 /active、/pending 轮询结果中，避免 3s 轮询反复调用。

**v4 防御：报告任务从未创建**：用户跳转 H5 后未上传附件即关闭，报告任务从未创建（waitingReportTask 无 report_id）——若仍按"生成中"等待，前端轮询永远 pending、report-completed 永不触发，管道永久挂起。修复：恢复时检测 report_id 为空 → 重新发出 redirect 卡（`supersede_redirect` 标记，取代穿插前段落旧跳转卡）引导用户再次跳转。

**Phase 7：外部异步任务归属（DeferredEvent 事件化）**：

```
PendingExternalTask 登记表（会话级：report_id → {externalTaskId, frameId, type, status}）
  ├─ 报告任务创建成功（report_id 写回）时登记，穿插挂起期间不清空
  ├─ 完成回调（report-completed）按 externalTaskId/frameId 精确定位归属帧，
  │   不依赖当前活动状态（currentFrame/company/pipeline）
  ├─ 目标帧 RUNNING → 正常消费；目标帧 SUSPENDED → REPORT_COMPLETED 事件入帧
  │   （frame.deferredEvents.add），禁止推进被挂起帧
  └─ 恢复该帧 → activeDeferredEvents 转移 → 消费事件（或兼容布尔 pendingReportDone）
     后决定继续 Pipeline 或等待其他事件；帧被放弃 → 事件随帧作废
```

### 3.6 前端任务清单卡（plan / switch / complete 三形态）

- **plan 卡**：管道开始时创建（初始计划，currentOrder=0）
- **switch 卡**：每次 task_start 新建任务切换卡（order>1），**同时更新首卡 currentOrder**
- **complete 卡**：全部完成时创建（绿色完成态）

三形态卡均以 `{"action":"pipeline",...}` JSON 持久化为 assistant 消息——切换会话/刷新后由前端解析 extra 恢复渲染，进度不丢失。升级细节：

- **frameId 定位**：恢复路径 planning(resume=true) 优先按 frameId 精确匹配历史任务卡（旧卡无 frameId 回退 plan 内容匹配，再回退最后一张卡）
- **任务卡完成态回填**：管道全部完成时历史中所有 plan/switch 卡标记 completed=true，与末尾绿色完成卡语义一致
- **supersede 语义**：穿插恢复补发的 progress/redirect 卡取代穿插前段落旧跳转卡（前端移除旧卡 + 后端落盘 hidden 标记）

## 四、意图穿插：管道执行中换需求（断点再续）

### 4.1 要解决的问题

多意图管道暂停时（如等待模板选择/参数补充），用户发来一个**与当前任务无关的新意图**（如"查询B公司历史尽调"）。若不做区分，该消息会被当作补充信息吞进管道恢复流程。

### 4.2 六层判定：补充信息 vs 新意图（IntentInterruptClassifier）

独立分类器 `IntentInterruptClassifier.classify`（实施文档第 13 节，**顺序不允许调整**），每次判定输出结构化日志 `INPUT_CLASSIFIED（frameId/result/source）`：

| 层 | 判定手段 | 判为"新意图"的条件 |
|:---:|----------|----------------------|
| ① | **Structured Protocol** | `【意图选择】` → 新意图；`【模板选择】` / `"以上都不是"` → 补充（机器可确定的协议交互，命中后禁止继续进入普通分类） |
| ② | **Explicit Interrupt** | 显式穿插信号词（顺便/另外/再帮我/同时/换个问题/先查一下/先别管这个/对了/还有一个事）+ **独立任务请求**（命中不同技能，或查询行为词+带企业名）——不允许单命中信号词就判 |
| ③ | **Expected Input** | 当前等待参数能否被满足：候选确认格式（`公司：xxx\n统一信用代码：xxx`）→ 补充；**等待附件时任何文本都不算补充**（放行后继续判定）；纯企业名（无查询词+缺 company_name）→ 补充；18 位信用代码 → 补充；日期范围（近一年/2024-01-01 到 2024-03-31/就查去年一整年）→ 补充；候选序号（第二个/选2/3号）→ 补充 |
| ④ | **IntentMatcher** | 确定性树匹配（仅对当前消息）：命中技能 ≠ 当前暂停技能（**matchable 预留候选视为新意图**）→ 新意图；命中相同技能且无新企业 → 补充；同技能+新企业 → 落⑤ |
| ⑤ | **Context Shift** | 含与上下文不同的新企业名 +（同技能命中 或 查询行为词）→ 新意图（"阿里的股东呢？"） |
| ⑥ | **LLM Fallback** | `classifyIntentInterrupt` 二分类输出 {"class": "supplement"\|"new_intent"}（失败保守返回 supplement） |

**为什么③必须先于④⑤？** 等待企业名时输入"阿里巴巴"会被新企业检测误判为新意图——先判定"当前等待参数能否被满足"，纯企业名直接归为补充，不会误穿插。

**为什么第④步用确定性匹配而非 LLM？** 判定必须快、可测试、可解释；且匹配只对当前消息文本做（树匹配本身不依赖历史），避免把管道技能自身的历史命中误判为新意图。

**误判代价分析**："补充信息误判为新意图"的后果仅是穿插后多一次"是否继续"询问（用户可选放弃），危害可控——这是设计上接受的权衡。

### 4.3 挂起栈：ExecutionFrame 执行帧（Phase 2）

`ContextMemoryService` 用 `Deque<ExecutionFrame> suspendedStack` 实现**挂起栈**（LIFO），栈元素为 `ExecutionFrame` 执行帧——一个可被完整保存、挂起、恢复、放弃的任务运行现场：

```java
suspendPipeline(convId):   // 穿插前调用
  frame = {
    frameId / parentFrameId:  任务标识与嵌套层级（日志追踪用）
    pipeline:                 剩余任务队列（pendingPipeline 拷贝）
    plan:                     完整计划快照（pipelinePlan 拷贝，前端任务清单重建依赖）
    pendingSkill:             暂停中任务（skill/params/hint/retry）
    waitingReport:            异步报告等待任务（报告生成期间穿插时非 null）
    companyName / creditCode: 挂起时刻的企业上下文（防止穿插期企业名漂移污染旧管道）
    attachmentUrl:            挂起时刻的最新附件 URL（穿插期间上传的新附件不漂移到旧管道）
    planRuntime:              Phase 3 计划状态视图（穿插期间新意图的计划不覆盖旧计划）
    deferredEvents:           Phase 7 挂起期间到达的异步完成事件（恢复时消费）
  }
  suspendedStack.push(frame)
  清空活动状态（pendingPipeline/plan/pendingSkill/planRuntime/interruptAskPending 等）
```

**为什么必须存 plan 快照？** 新意图若是多意图管道，其 `handleMulti` 会覆盖 `ctx.pipelinePlan`——不转移快照，恢复时前端任务清单就缩水了。同理存 companyName：穿插执行期上下文企业被改成 B，恢复后旧管道参数续跑以快照里的 A 为基准。attachmentUrl 同理（P4 隔离）。

**嵌套穿插**：穿插执行中再次穿插 → 新帧继续压栈（parentFrameId 记录被挂起任务的 frameId）。恢复/放弃只作用于栈顶一层；放弃栈顶后若栈中仍有下一层 → **立即询问下一层**（逐层决定）；直接发新问题 → **保留整个栈**（新意图结束后流尾会再次询问栈顶，不再隐式清空）。

**恢复校验（Phase 5）**：结构化恢复协议 `{"action":"resume_frame","frameId":"F001"}` 必须满足"正在询问栈顶层（interruptAskPending）+ frameId 与栈顶帧一致"才执行——允许恢复 B 时点击旧 A 卡 → `STALE_ACTION` 拒绝，禁止跳过栈顶直接恢复深层帧；活动任务执行中点击恢复卡同样拒绝（防止 pop 覆盖活动任务状态）。旧文本协议 `【管道恢复】继续/放弃` 继续兼容。

### 4.4 完整时序（核心链路）

```
用户：查询A公司历史尽调 + 生成尽调报告
  → multi → frameId=F1 → planning(2项, F1) → 查询A历史尽调结果卡 → task_done
  → generate_report 模板选择 → pendingSkill 暂停（管道暂停，步骤 WAITING_INPUT）

用户：查询B公司历史尽调报告
  → 主流程分支：管道暂停中 → routePendingInput → 六层判定
  → ④树匹配命中 query_due_diligence_reports ≠ generate_report → NEW_INTENT
  → handleInterrupt：suspendPipeline 压栈（帧含 pipeline/plan/pendingSkill/companyName=A/F1）
  → 分配新帧 F2（parentFrameId=F1）→ routeIntent 执行新意图
  → B 公司历史尽调结果卡（frameId=F2 贯穿事件与卡片）
  → 流尾 interruptAskCheck：挂起栈非空 + 无活动管道/技能 → 发 interrupt_ask 询问卡
    （frameId=F1 + interactionId + "您之前还有 1 项任务未完成（生成尽调报告），是否继续执行？"）

用户点击「继续执行」→ 发送 {"action":"resume_frame","frameId":"F1"}
  → handleStructuredResume：帧校验通过 → popAndRestorePipeline 弹出栈顶恢复
    （pendingSkill/plan/companyName=A 还原，currentFrameId 回填 F1）
  → handleMultiResume：planning(resume=true, F1) + 从模板选择断点恢复
  → 模板选择 → 报告生成 → 跳转 H5 → waitingReportTask 挂起（步骤 WAITING_EXTERNAL）
  → 前端轮询报告 completed → report-completed → 完成卡（2 项任务闭环）→ Plan COMPLETED
```

### 4.5 关键机制的巧妙之处

1. **流尾统一询问（interruptAskCheck）**：在 `chatStream` 返回流的尾部挂一个 `Flux.defer` 检查，"一次接入覆盖所有新意图稳定点"——穿插的是单技能/多意图管道/纯聊天，都不需要各自埋询问逻辑；穿插管道中途再次暂停则不询问（有 pending），直到最终结束的那一轮才触发。幂等：interruptAskPending 期间不重复触发。

2. **报告生成期间也能穿插（v3 + Phase 7）**：`isWaitingReport` 不再忽略消息，而是把 `waitingReportTask` 随帧压栈后执行新意图。穿插期间报告先完成 → `pendingReportDone` 标记 + REPORT_COMPLETED 事件入帧（report-completed 返回 deferred=true，前端跳过本地卡片处理），**恢复该挂起层时消费标记/事件就地推进**——防止"推进动作丢失导致管道死锁"。

3. **v4 防御：报告任务从未创建**：用户跳转 H5 后未上传附件即关闭，报告任务从未创建（waitingReportTask 无 report_id）——若仍按"生成中"等待，前端轮询永远 pending、report-completed 永不触发，管道永久挂起。修复：恢复时检测 report_id 为空 → 重新发出 redirect 卡（supersede_redirect）引导用户再次跳转。

4. **交互 ID 化（Phase 6）——旧卡点击防护**：企业候选选择/意图澄清/模板选择卡事件生成时携带生成帧 frameId + interactionId，点击回传后校验 `frameId == 当前活动帧`——A 挂起、B 活动时点击 A 的卡 → `INTERACTION_SUSPENDED` 拒绝（前端禁用只是 UX，后端必须执行 frameId 校验），禁止把挂起帧的交互值传入当前活动任务；校验通过后转发等价文本走现有判定路径，语义与旧文本协议完全一致。

5. **自然语言兜底（interruptAskPending 期间直接输入）**：确认短语（继续/需要/好/可以…）→ 弹出栈顶恢复；放弃短语（不需要/算了/取消…）→ 丢弃栈顶（若有下一层继续询问）；其他内容 → **保留挂起栈**，按正常三层路由执行新消息（新意图结束后流尾再次询问栈顶，旧任务不丢）。

### 4.6 意图穿插的适用范围（重要边界）

- **只服务多意图管道场景**：单意图对话中"以上都不是"否决候选后残留的 pendingSkill 不再触发穿插压栈（`pendingSkillRejected` 标记）；用户随后发起新意图时清除残留状态直接三层路由，**避免单意图对话出现"任务中断提醒"**。
- **候选否决兜底**："以上都不是"在主流程统一拦截（返回友好提示、保留 pendingSkill 但清空已否决的企业参数、标记 pendingSkillRejected）；handleSkill 内还有第二道防线（技能调用前拦截），防止清洗链把该文本当企业名再次模糊匹配弹候选卡死循环。
- 例外：`【管道恢复】` 前缀消息（历史询问卡点击）在报告生成期间提示等待而非恢复（栈顶可能仍是更早挂起层，恢复会与等待中的报告冲突）。
- 后端重启：挂起栈为内存态，重启丢失 → 旧管道隐式放弃；`interrupt_ask` 卡片已持久化仍可点击（answered 标记置灰），恢复动作校验失败返回 STALE_ACTION 可见反馈（防御：空栈时不再静默无响应）。

## 五、面试高频问题（Q&A 速查）

**Q1：为什么意图识别要做成三层，而不是直接让 LLM 决定？**
确定性优先原则。全 LLM 方案：不可解释、不可测试、每次都要 LLM 调用（成本+延迟+不稳定）。三层架构让 80% 的常见意图在毫秒级确定性路由（树匹配），唯一候选还能直接提取参数零 LLM 完成；LLM 只在多候选仲裁、空候选兜底时介入，且"LLM 只做选不做猜"。

**Q2：分层意图树相比扁平关键词匹配有什么优势？**
1) 层级互斥由树结构承担（历史/最新/得分天然互斥，无需 conflictGroup 配置）；2) defaultLeaf 表达"同域兜底"语义（兄弟全不中才激活）；3) 剪枝提升匹配效率；4) 新增业务 = 加叶子/子域，结构化可读可测；5) matchable 预留节点让"未开通业务"有明确语义而不是静默误路由；6) 同技能多叶子命中自动去重。

**Q3：defaultLeaf 怎么防止"查询/查一下"这类泛化词劫持具体意图？**
全局意图词黑名单（mustNot）：其他域/叶子的核心词（风险/海关/股东/授信/营业执照/核实…）出现在输入中即放弃基本信息兜底，交给具体叶子或 LLM 兜底/澄清。同时"核实对象不明"由 branch_21 兜底叶子承接（虚拟技能 verify_ambiguous → 澄清卡），不硬猜核实类型。

**Q4：多候选时为什么先 LLM 仲裁而不是直接澄清？**
仲裁成本低于澄清交互（一次 LLM 调用 vs 一轮人机往返）；只有仲裁置信度 < 0.6 才转澄清。同时仲裁支持 multi 输出（一次识别多个意图），澄清只能二选一。

**Q5：意图穿插怎么区分"补充信息"和"新意图"？**
六层判定（顺序不可调）：① 协议前缀（【模板选择】补充 /【意图选择】新意图）→ ② 显式穿插信号词+独立任务请求 → ③ 预期输入（当前等待参数能否被满足：纯企业名/信用代码/日期/候选序号/候选确认格式 → 补充）→ ④ 确定性树匹配（命中技能≠暂停技能 → 新意图）→ ⑤ 上下文转移（同技能+新企业/企业切换+查询词）→ ⑥ LLM 二分类兜底。前五级零 LLM、可测试，LLM 只做最后兜底。

**Q6：嵌套穿插（A 管道中穿插 B，B 中又穿插 C）如何保证正确恢复？**
挂起栈 LIFO + ExecutionFrame 执行帧：每次穿插把当前活动状态（pipeline/plan/pendingSkill/waitingReport/companyName/creditCode/attachmentUrl/planRuntime）打包成帧压栈，恢复只弹栈顶一层（frameId 校验保证不能跳过栈顶）；放弃栈顶若仍有下层立即询问下层，逐层决定；直接发新问题保留整个栈（流尾再问栈顶）。穿插期间异步完成事件随帧保存（deferredEvents），恢复时消费。

**Q7：异步报告生成和同步管道如何同步？**
waitingReportTask 记录等待任务 → 前端轮询报告状态调 report-completed 推进（最后任务：完成卡收尾；中间任务：升级为 pendingSkill 续跑）；穿插期间报告完成 → pendingReportDone 标记 + DeferredEvent 事件入帧，恢复时消费就地推进；报告任务未创建（用户未上传附件）→ 恢复时重发 redirect 卡。轮询按 reportId 去重（前端 Set + 后端 consumed 标记双保险），防止刷屏。

**Q8：上下文记忆服务承担什么角色？**
按会话维护：companyName/creditCode（企业上下文补全）、pendingSkill（单技能暂停 + pendingSkillRejected 否决标记）、pendingPipeline/pipelinePlan（管道暂停+计划快照）、attachmentUrl（附件注入，穿插时随帧隔离）、suspendedStack（ExecutionFrame 挂起栈）、waitingReportTask（报告等待）、currentFrameId/parentFrameId（任务标识）、planRuntime（Plan 状态视图）、externalTasks（外部异步任务登记表）、activeDeferredEvents（恢复时的事件缓存）。技能执行前自动补全共享参数（独立补全互不连坐 + 同一企业判定走统一清洗链），用户无需重复输入。

**Q9：状态都是内存态，崩溃/重启怎么办？**
交互状态（暂停/挂起/PlanRuntime）内存态丢失可接受：管道隐式放弃；但**可见卡片全部持久化为 assistant 消息**（plan/switch/complete 卡、interrupt_ask 卡、澄清卡、候选卡），刷新/切换会话后前端从历史解析 extra 恢复渲染；询问卡 answered 标记、候选卡 confirmed 标记、管道卡 completed 标记随消息落盘保持置灰/完成态；恢复/交互动作带 frameId 校验，失效点击返回 STALE_ACTION / INTERACTION_SUSPENDED 可见反馈，不静默失败。

**Q10：这个系统里你最得意的设计/踩过的坑？**
可选素材（真实经历）：
- 询问卡显示"还有 0 项任务"bug：挂起快照含多维度，但摘要生成只读 plan 维度，被挂起的是"候选确认卡"（只有 pendingSkill）时摘要为 0 → 改为 `peekSuspendedRemainingTasks` 综合 pendingSkill/waitingReport/pendingPipeline 各维度构造摘要（order 反查完整计划），非空才发询问卡。
- 报告穿插死锁：报告完成推进动作与穿插恢复的时序竞争 → pendingReportDone 延迟消费 + Phase 7 DeferredEvent 按 externalTaskId 精确归属帧。
- 单意图误穿插：残留 pendingSkill 触发"任务中断提醒" → pendingSkillRejected 标记隔离。
- 轮询刷屏：/active 与 /pending 双轮询重复调 report-completed → 前端 processedReportIdsRef 按 reportId 去重 + 后端 consumed 标记双保险。
- 候选卡重复确认：刷新后前端本地点击计数丢失，再次点击企业走候选确认而非功能查询 → confirmed 标记持久化 + 乐观更新。
- 企业名漂移：穿插期上下文企业被改 B，恢复旧管道用 B 续跑 → ExecutionFrame 快照携带 companyName/creditCode/attachmentUrl 还原。
- 澄清后参数丢失："核实星河信息"点选意图后被上下文自动填成小米科技 → 澄清卡持久化 user_input，select_intent 时恢复原始输入 LLM 提取参数。
